SAVE, ECONOMY & ANTI-CHEAT

Other Systems › Save, Economy & Anti-Cheat

One doctrine underneath everything: the client sends events and requests, never state. The local save is a disposable prediction cache, overwritten on every server reconciliation — editing it is inert, not forbidden. This page is the distilled, validated summary; the full technical spec is SAVE_ARCHITECTURE.md (v2).

The transaction contract

Every economic action is: check server balance → atomic debit + grant → or reject whole. Nothing partial, nothing client-computed. Two mechanisms make "atomic" real rather than aspirational:

MechanismWhat it stops
Idempotency keysEvery request carries a unique key; replays of the same request are no-ops. Retried packets and deliberate double-sends cannot double-grant.
Version tokens (write locks)Cloud Save writes are compare-and-swap on a version token. Two simultaneous spends that both read balance 100 cannot both commit — the second fails and re-reads. This is the actual historical dupe vector: Diablo 3's trillions-of-gold incident was a transaction-layer race in its own auction house, not a hacked client.

Reward path & the accrual cap

The client reports what happened (battle event logs); the server derives reward values from its own tables — a client cannot name a number. On top of that sits the single cheapest, strongest control an autoplay game can have:

Wall-clock accrual cap. Rewards credited per flush are capped by elapsed real time (~30 battles/hour at autoplay pace, with headroom). A client claiming 4,000 battles in ten minutes is not investigated — it is arithmetically impossible and clipped at the ledger. Farming faster than time permits cannot be expressed in the protocol.

Verification — trust, but replay

EventVerification
Boss kills, floor/ladder advances100% seeded-replay verified: the server issued the encounter seed, the client submits the move log, Cloud Code re-simulates deterministically and compares the claimed result. Value-gating events are never taken on faith.
Ordinary grind battlesRandom sampling + statistical invariants: monotonic XP, battle-rate plausibility, streak-threshold consistency, drop-rate bounds, currency reconciliation. Cheap to run, expensive to fool at scale.
Rated PvP matchesEvery match ends with one deterministic replay adjudication — full spec on PvP, Timers & Persistence (team legality by recompute-from-inputs, commit–reveal rounds with reveal-derived RNG seeds, per-round state checksums, replay as final authority).

The residual threat: farm accounts

Once client cheating is inert, the economy's remaining attacker plays legitimately — fleets of accounts running real autoplay to print tradeable items. Mitigations, in order:

GateEffect
Steam's $5 limited-account gateMarket and trading are locked behind Steam's own spend threshold — each farm account has a real cost floor.
Progression-gated market unlockTrading unlocks only past a progression milestone; a farm account must invest real climb-time before it can sell anything.
Listing velocity monitoringAccounts whose listing rate is inconsistent with their play pattern get flagged for the audit queue — the CS:GO key-fraud lesson: watch the exit, not just the faucet.

Leaderboards are server-derived (ANTICHEAT 2, 2026-07-30)

The studied model is Steam's Trusted writes: leaderboard scores cannot be set by clients — only the publisher's own server may write them. Client-writable boards die predictably (every Papers, Please endless board tops out at a forged 2,147,483,647). Herumon Tower follows the same rule: /api/lb/submit is retired (HTTP 410) and no client-callable board write exists. Every board value is derived from truth the server already owns:

BoardSource of truthWrite policy
ladderThe server-owned Elo. Folded from the ratings table once per snapshot day, at the board's own recut — finish-time board writes were removed the same day (D ruling): the board read is daily anyway, so per-match freshness was invisible and cost a write per match. Ratings live in the world object, so the fold is a bounded in-object pass over pvp-active players; unchanged rows bill nothing.set — the ladder shows the current rating; the row's first-arrival timestamp is kept.
climbThe maxFloor ratchet (progress), advanced only by credited battles. When a battle ratchets, the player object annotates its response and the Worker relays the new value to the world object under waitUntil — objects never call objects, and the player's response is never delayed.max — keep-best; monotone by construction. ~1 write per floor per player lifetime.
powerThe one value with no server recompute yet (that is ANTICHEAT 5). It rides the save as pw, is stripped from the stored record, and is validated in the player object against POW_MAX = LB_POW_BASE + LB_POW_PER_FLOOR × (ratchet+1) (env-tunable; defaults 2,000 + 1,500×f, calibrated from live data: 3,380 power at maxFloor 5 → ~3× headroom).max — keep-best, deadbanded (only an improvement over the last published value is relayed, so a 10-second autosave cadence can never become a world-write cadence). The validated value also persists in the database (pwlast, 2026-07-31) so the daily fold can serve it forever after. The climb ratchet also rides the save the same way; the world's keep-best absorbs any redundant publish.

The daily database fold (D ruling 2026-07-31: "the database needs to populate the rankings once a day — logging in should not change anything"). The daily backup sweep — the Worker cron that already walks every registered account to mirror saves — now carries each account's board facts back in the same hop (ratchet, persisted validated power, backend name; zero additional per-account requests) and folds every board through one batched sealed write per page, then drops the day's snapshots. Live event publishes remain as same-day freshness on top; the fold is the completeness floor that makes the boards independent of who happens to log in. Power itself is computed server-side (2026-07-31): src/power.js is a line-faithful port of the client engine's charPower() closure — item implicit grids, sockets, souls, class and creature math — parity-gated to EXACT equality against the live client on real saves before it ever touched a board. The fold derives every account's power from the save it is already carrying (mode set: power is the current build and drops when gear does), so every account with a save is on the board — no client involvement at all. The client's pw claim is demoted to telemetry: it persists as pwlast and the fold cross-checks claim vs computed, surfacing any mismatch (a port bug or a forged claim — both must be seen).

  • Breach = quarantine, never clamp. A power claim over the ceiling is flagged (lb_power_over) and writes no row — a cheater is absent from the board, never parked at the ceiling — and the save itself is stored untouched.
  • The first-there tiebreak is unforgeable: at is stamped by the server at the moment of the improvement. The retired submit route accepted a client at, which let a forged at:1 win every tiebreak forever; that class of input no longer exists.
  • A lower value never erases a stored best (the retired route's INSERT OR REPLACE could).
  • Rider, same batch: a battle event's floor is now clamped to ratchet+1 before it prices kills or advances anything (battle_floor_over flag). A forged floor-50 event used to ratchet — and would have boarded — 50 floors in one request; clamped, a fake climb costs one credited battle per floor through the spawn budget and rate caps, the same cost class as playing. The full enter-proof (require the floor's floors_srv row) stays on the Phase-2b list.
  • Reads are unchanged: the daily lb_snap top-100 behind a 30-minute edge cache, the daily rank pass for exact ranks, and /api/lb/purge as the removal tooling. Ops also has a one-shot climb backfill (key-gated, 2026-07-31): board rows are born on each player's next save — correct forever, empty-looking on day one — so the backfill walks the account registry, reads each live save (maxFloor is ratchet-clamped at save time) and upserts climb through the same sealed route the relay uses, then drops the day's snapshot so the rows show today. Power cannot be backfilled (client-derived); ladder already folds from ratings.
  • Board display names come from the world name/claim identity (claimed at character creation); an account without one shows Climber.

Failure & cost doctrine

Precedent says the model holds: the mobile-strategy pattern this follows (client as pure view, all authority server-side) is why modded clients achieve nothing against such games. Its known failure modes are the transaction layer (handled above) and cost blowout — the naive build of this same architecture (UGS Economy ledgers, per-round PvP server resolution) priced at >$450k/month at 500k CCU; the committed build lands at ~$0.02–0.03 per concurrent user per month (~$12–15k/month at 500k CCU), dominated by batched Cloud Save writes. Flush tiers: immediate for stakes (deaths, trades, ladder), batched for grind accrual.

A throw in renderVals is a blank screen, not a broken row

renderVals() builds the entire flat object the template renders against. It is all-or-nothing: one exception anywhere inside it and every {{ binding }} on the page fails to resolve at once. The player does not see a missing name — they see the whole screen vanish, and then reappear seconds later when the next good state renders.

Report #20 is the worked example. A wild spawn whose row could not be resolved (Spawn '?' has no Line_ID in creatures.csv) becomes a unit with name === undefined. confirmRows did tn = u[q.target].name and then sized the label with targetFs:(tn.length<=11 ? 18 : ...). The read threw, renderVals died, and the page went blank mid-battle. The player's log tape shows it exactly: an asset failure on codex/images/med/undefined.webp, then TypeError: Cannot read properties of undefined (reading 'length'), then eleven consecutive never resolved — rendered as empty warnings for round, streakX and every unit portrait in one burst. That burst is the signature of this failure class.

An empty string is not the same as undefined, and this is the trap. ''.length is 0 and renders perfectly; only undefined throws. A reproduction built with name: '' therefore looks completely healthy and proves nothing — which is exactly what happened on the first attempt to reproduce this. tools/probe_r20.py keeps both as controls for that reason.

The doctrine. Anything renderVals reads that ultimately came from a CSV row, a spawn descriptor or a save is data, and data can be absent. Never read a property off it unguarded, and never read .length off it at all without a fallback. The cost of being wrong is not a cosmetic defect — it is the whole client, mid-battle.

Client: confirmRows in renderVals(), play/app.js. Probe: tools/probe_r20.py (4/4).

A battle is priced against the floor it was clamped to, not the floor it claimed

Most of this was already closed and the surviving notes about it were stale. Verified against a real worker, not read: ANTICHEAT 2 clamps the event's floor to ratchet + 1 before it prices anything; STAGE 4b derives the primary kill from the server's own seeded slot so the client's claimed tier and level for it are ignored outright; extras clamp to the primary's tier and floor ±3; with no slot every claimed kill clamps to the floor's own weight table; and _table is injected by the Worker, so a client-supplied one is overwritten.

What was still open was a sequencing mismatch between two individually-correct steps. The Worker fetches the spawn table for the claimed floor, because it must — the object may never be handed the spawn data. Only afterwards does the object clamp the floor. So on a forged claim the table described floor 99 while the pricing described floor 2, and the tier check asked "can floor 99 spawn an SSR?" Rarity is a 7× multiplier on both XP and Ichor.

Measured before the fix: a forged floor-99 SSR claim paid 18× the XP and 9× the Ichor of an honest floor-1 kill, on an account whose ratchet was 1. Bounded by the rate cap and the spawn budget, so not unlimited — but this is the value per battle gap, which those caps do not address at all.

Fix: the Worker stamps _tableF with the floor the table describes. The object compares it to the clamped floor and, on a mismatch, refuses to price against it: the slot path will not derive an identity from it, the tier check falls back to Common, and it flags battle_table_mismatch. The battle is still credited — a confused client should not lose a fight — it simply cannot be paid for a floor the account cannot reach. An honest client never claims above ratchet + 1, so the clamp never fires for it and the stamp always matches.

Measured after: 1.0×, like-for-like against an honest Common at the same clamped floor and the same legitimate +3 spawn level.

Three false readings on the way, all in the test rather than the code, and worth recording because each one first looked like a finding: a missing x-ht-epoch header made every forgery "refused" for the wrong reason; a floor-1 baseline against a claim that clamps to floor 2 read as 2.5× residual; and a level-2 baseline against a legitimate floor+3 spawn read as the same. Only a comparison whose own controls pass means anything.

Worker: _tableF stamp on the /api/battle pre-pass. Object: tblOk in the battle handler. Probe: tools/probe_battleclaim.py (3/3).

Changelog

2026-08-29 — a battle chain no longer diverges silently (#638). ON DEV, not yet on release. The chain check reported battles arriving on a head the server never issued. The account it fired on also sent a stale save and a short codex the same day — three detections, one device whose local writes were not landing. The client advances its chain head and stores it; that store sat in a silent catch, so a device with a full browser store moved the head in memory, failed to write it, and on the next reload sent the old one — a break on every battle from then on, looking exactly like a forged claim. The head is now read back to prove it landed, and if it did not the chain is abandoned so a fresh one starts: one flagged break instead of permanent divergence. Two things found and not changed: the check still refuses nothing and overwrites its stored head with whatever arrives, so it repairs itself to the claimant's version; and the answer carries a verdict field the client has never read. Enforcing is a separate decision, because it would refuse credit to a legitimately resumed battle.

2026-08-29 — a mass dismantle stops re-reading the whole ledger for every item (#632). ON DEV, not yet on release. One batch wrote 173 ledger rows against a normal ten an hour, and the question was whether that many rows are needed. They are — each row is keyed to the item that produced it, and that key is the only thing that makes a retry safe; the item's tombstone is explicitly not, because a stone unsocketed and dismantled in one flush has to be re-verified from scratch. Merging them would double-credit a retry that overlapped a previous one. The cost was never the rows. Each one scanned the entire ledger to check its key, and summed the whole balance twice — once to compute and once to check for drift. That is 519 read operations for one dismantle. The batch now takes one scan and carries each currency's balance forward, with the drift check running once per currency at the end: 519 reads become 11, the same guarantee for a forty-seventh of the work. No index was added, because an index entry is itself a written row on every insert.

2026-08-29 — two detectors stop flagging the server's own arithmetic. ON DEV, not yet on release. The currency-rate guard was reporting bulk dismantles as suspicious income: the Ichor burst allowance is 1,500 while one batch pays far more, and the same account in the same hour shows 173 dismantle rows in a single request. The server had booked that income itself, so the guard was flagging a payout it had just made; the booked amount now joins the allowance, exactly as the Shadow Trader's credit already did on the line above. The clamping tier is untouched and remains the only one that ever refuses anything. Separately, the egg-claim check flagged pens finishing one second early on forty minutes — three anomalies across three days measured at 0.13%, 0.04% and 1.08%, all of them anchor drift and device clock skew. It now allows the greater of sixty seconds or two per cent of the pen, and anything past that still flags and still reports by how much. A detector that cries wolf gets ignored, which is the whole reason both were worth fixing.

2026-08-28 — the floor cache keeps the last five floors instead of all of them. ON DEV, not yet on release. The client kept the full encounter for every floor it had ever visited — each of a floor's ten slots holding its creature and the two battle opponents the server sends with it, so ~13 KB a floor and ~1.58 MB across a full tower. That was sixty per cent of everything the device is allowed to store, larger than the save and every battle log put together, and nothing had ever removed an entry. Nothing is lost by dropping one: the server derives each slot from a keyed hash of account, realm, floor, version, slot and sequence, so it reproduces the identical encounter on demand — and the game already asks it for the floor's truth every time you arrive. The cache only paints the screen for the moment before that answer lands.

2026-08-28 — a battle can no longer start against a spawn that is already gone. ON DEV, not yet on release. A player on floor 19 saw “Spawn ‘?’ has no Line_ID in creatures.csv”. The data was innocent: that floor's ten creatures resolve on live codex and at the pinned copy release serves, and the server can only pick ids it read from the same table. Autoplay picks a slot, cues a 650 ms pan, and starts the fight on a timeout — and any floor sync inside that window replaces the whole pool. The queued start re-checked autoplay, phase and transit but never that the slot was still there. A slot the server reports empty carries no name and no line, so the fight opened against a creature called undefined with a placeholder move set — the same shape of unresolved unit that once blanked the entire battle screen. The click path could never do this, because a dead slot draws nothing to click; only a stale index reaches it. The target is now checked where it is used, and a moved pool triggers a resync.
