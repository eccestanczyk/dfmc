NETWORKING ARCHITECTURE

Other Systems › Networking Architecture

How the client and the backend talk, what each side is allowed to decide, and what every call costs. Read this before changing anything in src/worker.js or any code path that makes a network call. The stack is Cloudflare Workers plus SQLite-backed Durable Objects. The older Save, Economy & Anti-Cheat page describes the retired Unity/UGS design and is kept for its doctrine only — its named services no longer apply.

Doctrine

RuleMeaning
Clients send events and requests, never stateThe save is a prediction cache. A server reconciliation overwrites it. Editing it should be inert.
Nothing happens offlineOffline play is banned outright. No queue, no outbox, no banking, no replay of work done while disconnected. On loss of connection autoplay pauses, the battle pauses, and a reconnecting window shows. Play resumes only when the connection returns.
Ownership is fenced by the server, not asserted by the clientAdopting the save mints an epoch; every later request carries it and the object refuses any instance holding a lower one. A check a client performs on itself is worth nothing once the client is the thing that is broken.
A dead writer is a dead channel“Offline” means the writer, not the socket. A window that can no longer save takes the same path as a lost connection — play pauses — because /api/battle is a separate writer and keeps crediting a window whose save has stopped moving. The one difference: a write halt is terminal, cleared only by a reload that re-adopts the server copy. Never by a client-side merge.
The server derives rewardsThe client reports what it did, never what it earned. XP, food and drops come from server tables, and the client applies what it is told.
Cost scales with battles, not with time connectedAn idle account must write nothing. If a player is doing nothing there is nothing to save.

⚠ Durable Object rules — a 1000× cost risk

Duration is billed in wall-clock time at the full 128 MB allocation whenever an object is active or idle but unable to hibernate. An idle object that qualifies for hibernation is not billed at all. Hibernation requires all of: no setTimeout/setInterval, no in-progress awaited fetch(), no standard WebSocket API, and no request still being processed. It then hibernates after 10s idle.

Nothing inside a Durable Object class may ever use setTimeout, setInterval, a plain WebSocket accept(), or an awaited fetch(). Any one of them makes the object permanently non-hibernateable. With a request arriving every few seconds the object then never leaves the billed idle state.

Cloudflare's own guidance is “do not create a single global Durable Object that handles all requests” — which is exactly what idFromName('main') is today. Their Queues team hit the same wall at ~400 msg/s and only got a 10× speedup by sharding into consumer-shard objects. Shared objects must therefore be sharded too: a single leaderboard object is the same mistake at a smaller scale.

Objects never call each other. The Worker orchestrates. A PlayerDO that awaits a fetch() to another object blocks hibernation for the whole round trip and bills for the wait — it is the same mistake as an open socket, wearing an internal address. When a battle needs both a player write and a leaderboard submit, the Worker calls each in turn.

Scheduled work is a Worker scheduled() cron that calls into the object. Never a DO alarm: setAlarm() is itself billed as a row written and keeps the object awake. Also standing: no unqualified DELETE or SELECT in a constructor, and one-off migrations claim their completion flag before doing the work.

How a sync is queued

Release status. Everything in this section is live on release 0.25 except three client changes that are on DEV only and not yet on release, marked DEV below: the hidden coalesce, the non-OK re-arm, and (in the next section) the shell writing both run keys. The backend half is identical on both branches — src/worker.js is byte-for-byte the same file on main and dev.

There is no queue in the durable sense and there must never be one: the doctrine bans banking work done offline. What follows is a deadline and a dirty flag, both of which live in the page and die with it. Nothing is replayed from a previous session, and a re-arm always resends current state, never a recorded intent.

MechanismAs built
The deadline takes the minimumqueueFlush(ms) sets _srvFlushAt to min(existing, now + ms) and marks _srvDirty. So a lazy 5-minute autoplay deadline is tightened to 10 s by the next manual action rather than replaced by whichever call happened last.
The heartbeat fires itmaybeFlush() runs on the rAF ticker and compares against Date.now() explicitly — the ticker passes performance.now(), a different clock domain, and comparing the two never fires at all.
One write in flight at a timeA flush issued while another is unsettled is chained behind it and re-runs once the first has landed and refreshed _srvVer. Without this, two overlapping writes from the same session carry the same base_ver, the second is refused 409, and the client — correctly following its own rule — concludes another device owns the run and reboots onto a pre-ascend copy. Reported live as “kicked down a floor when ascending”; nothing about it involved a second device.
Unload writes cannot chainA pagehide or keepalive write cannot wait on a promise the page will not live to settle, so it re-arms the dirty flag instead of queueing behind the in-flight one.
Nothing to save is nothing to senddebounce, hidden and pagehide all return early when _srvDirty is false. Before this, a session the player never touched uploaded its whole state the moment a tab was backgrounded.
hidden is coalesced, pagehide never is DEV visibilitychange→hidden fires on every screen-off, notification pull and app switch, which on a phone is constant, and each one used to spend a token from the save bucket. Throttled to one flush per HIDE_COALESCE_MS (15 s, matching the 429 retry_ms), with _srvDirty deliberately left set when a flush is skipped so nothing is dropped and the heartbeat carries it. Backgrounding is recoverable because the page survives; a close is the last chance there will ever be.
Re-arm rules, by answer DEV2xx — clean, adopt srv{}. 409 — never re-arm; this window is stale and resending is precisely the wrong move, so it reboots onto server truth. Any other non-OK (429, 413, 403, 5xx) — re-arm and honour retry_ms when the server gives one, else 10 s. Network throw — re-arm at 10 s and fire the connection check immediately.
Why not sendBeaconIt cannot set custom headers, so it cannot carry x-ht-epoch — and the fence treats a missing epoch against a non-null session epoch as a mismatch. Exempting beacons would reopen exactly the bypass the fence exists to close. fetch(keepalive:true) can set headers, which is why it is used.
Open, and it interacts with the save ceiling. A keepalive request body is capped at 64 KB by the Fetch standard while a save is allowed up to 131,072 bytes. Any save past 64 KB therefore cannot be flushed on unload at all, and the largest accounts are exactly the ones with most to lose. Unverified against the runtime; if it holds, the unload path needs a smaller payload, not a bigger allowance.

Re-simulation: considered and rejected (D ruling)

Deterministic replay does account for player choices — the choices are the inputs, and for autoplay there are none to send because the heuristic is deterministic. It was rejected anyway, because it requires the battle engine to run server-side, which is the engine-extraction job already ruled out. Do not re-propose it as a cheap addition; it is that job wearing a different name.

What the power gate does not catch, accepted knowingly: a forged win in a fight that was plausibly winnable, and an understated turns count (which feeds the rate cap). The exposure is bounded because the server already owns what spawned, whether the battle could be entered, and what the rewards are — and the spawner caps a player at 60 battles an hour. The most a forger converts is some losses into wins, at a rate they were already limited to, visibly out of line with their power in the statistics.

Blanket server-side resolution of every battle is deliberately not planned — extracting the engine into a module both sides import is the largest job on the table. The documented industry line is the split above: full re-simulation for the competitive surface, plausibility gates and sampled auditing for grind. The idle RPG Firestone runs this exact model — 99% server-side with the main battle left client-side because the calculation volume does not justify it — and catches the residual with statistical flagging, reporting roughly 1% of new players banned daily at fewer than 1 wrong call in 500 reports. Note the corollary: flags feed a human queue, they do not auto-ban.

Save authority — which copy wins on login

The server save is authoritative. If the server holds a save for a realm, that save wins on login, unconditionally. The local copy is used only when the server has nothing for that realm, which is a first login on a browser that already carries progress; that one copy is pushed up and becomes the server's.

Server has…Local has…Result
a saveanything, any ageServer save adopted into localStorage. If the local copy carried later work, that work is discarded and the in-progress battle snapshot is dropped with it — a battle snapshot belongs to the save it was taken from.
nothinga save at the current SAVE_EPOCHLocal kept and posted to the server.
nothingnothing, or a pre-epoch saveCharacter creation.

Why not the newest copy. Adoption used to pick whichever save carried the later ts. That stamp records when a browser last wrote, not how far the save got, so a browser left on old progress won every conflict simply by being opened last — and then posted its old state back up. It also put the decision in the hands of the client clock, which is arbitrary: a machine with a skewed clock would win every conflict forever, or lose every one. No timestamp comparison between two clients can be trusted, so none is made.

Two server-side gates remain behind this and are unchanged: a write whose ts precedes the stored one is rejected 409 stale, and a write whose playerXp is under half the stored value is rejected 409 xp regression flagged. Note that floorNum and maxFloor carry no regression gate of their own — the login rule above is what keeps a stale client from walking them backwards.

Why the seed moved server-side (2026-08-02). It used to be minted by the CLIENT: on load, an account with no wgSeed flag set its own wallet to WG_SEED and claimed the flag in the same write. That is correct shape for a client-side migration and wrong for money. The ceiling above is held = previous stored Wraithgold, so for any account that ALREADY had a save when the seed shipped (2026-07-27) held was 0, the claimed 100 was clamped straight back to 0 and flagged wraithgold_over_grant — and the client never retried, because it had already written wgSeed:1. The rule to take from it: a client-side one-off cannot mint anything the server ratchets. If the server owns the ceiling, the server owns the grant.

An entitlement row was the other candidate shape and was rejected: nothing on the client applies pending entitlements yet, so the credit would have lifted the ceiling and never reached the wallet.

ONE WRITE IN FLIGHT AT A TIME. base_ver is optimistic concurrency: a write lands only if the version the client echoes is still the one the server holds. It follows that two overlapping writes from the SAME session are indistinguishable from a second device — both carry the same base_ver, the first bumps the version, and the second is refused 409. The client then does exactly what it is told to do with a 409: concludes it is the loser, stops saving, adopts the server copy and reloads. That copy predates whatever the losing write was carrying, so the player is thrown backwards.

Reported live 2026-08-02 on a single device: “frequently getting this error and getting kicked down a floor when trying to ascend a floor.” The ascend is precisely where it bites — preloadFloor() forces a floor-entry flush, and the rAF heartbeat can fire the 10s debounce flush in the same breath. Writes are now serialized: a flush issued while another is in flight is CHAINED behind it and re-runs once the first has landed and refreshed the version, so it never sends a stale base_ver. Unload writes (pagehide, keepalive) cannot wait for a promise the page will not live to settle, so they re-arm the dirty flag instead of chaining.

The general point: a concurrency primitive that cannot tell your own second write from someone else’s turns every self-race into a false conflict — and a false conflict here is indistinguishable, to the player, from data loss.

The server says what it changed. An accepted write answers with srv:{} naming every field the server overrode, and the client adopts those values. A clamp that returns 200 OK and quietly eats progress is data loss with a success message on top; that is exactly how a stalled ratchet cost two players sixteen and ten floors and hours of xp.

Why it is built this way. Every shipped save service resolves the same problem with a version token the client echoes, and refuses the stale writer rather than merging or clamping it: PlayFab (ETag + If-Match → 412), Unity Cloud Save (write locks), Nakama (object versions), DynamoDB (conditional writes), Google Play Games (both conflicting snapshots returned, resolved by highest progress). None of them resolve conflicts by client clock, and none silently reduce a submitted value. Earned progress is a grow-only counter — it merges by max, so a late arrival from a stale device can never subtract.

Server-owned outcomes — the roll door

Chance belongs to the server. Deterministic work belongs to the client. That split is the ruling (2026-07-31): drops, upgrade attempts, egg hatching and breeding results are told to the client and never reported by it; equipping, unequipping and dismantling are deterministic, so the client performs them and they are validated in the next exchange by the save-door rules above.

POST /api/roll — session-gated. The Worker resolves the authored row from the codex CSVs (grading.csv, soul_grading.csv, breeding.csv; pinned to DATA_PIN on release and to main on dev, module-cached) and hands it to the player's object, exactly the way /api/floor/enter hands over its floor table — a Durable Object may never await a fetch. The object draws with HMAC-SHA256(SPAWN_SECRET, "roll|sid|realm|kind|idem"), the same keyed generator the spawn table uses, records the outcome and answers it.

Server-owned but not yet wired: egg hatching results and upgrade attempts — the doors exist and are probe-verified, but the client still rolls those locally until their batches land. Still client-side: boss guaranteed loot, zone keys and the first-win ladder, which the backend does not roll at all yet.

How a wired outcome reaches the screen. Deterministic rewards (XP, Ichor) are computed and shown the moment the battle ends, because nothing about them is chance. The chance-bearing part waits for the server: the client posts the battle, and the resolved drops are granted when the response lands, inside the victory bar’s own fill animation. Space is checked through the same bag guard as any other grant, so a full bag loses the drop rather than overflowing. If the player has already left the victory screen the items still land in the bag. Nothing is banked offline: a failed post grants nothing and forces the connection check, which pauses play.

The grant lane — retired 2026-08-05

The drain is off. Everything below describes how the lane worked until v0.34 and is kept as the record of why it was switched off, not as current behaviour. Drops arrive inline at the end of each battle; there is no catch-up on load. The lane itself disappears in the server-authority rework, when the server holds the bag and there is nothing to catch up on.

Why it was switched off

Two faults made it do more harm than good. The owed list was computed from the stored save’s grantAck, and that field was written to the save but never read back on load — so every page load began with an empty acknowledgement, the first save afterwards overwrote the stored history, and the server re-owed everything it had already handed over. Players came back to bags past their cap. And the drain filtered the offered items on having a name, which eggs do not carry: it found nothing to place, and acknowledged the grant anyway. Ninety-three eggs were destroyed that way and 1,357 more were queued to follow; 785 of those were formally revoked on 2026-08-05 and the remainder sit dormant.

How it worked, for the record

The rule. pendingGrants(steamid, realm) = every row in item_grants that is minted, not revoked, and whose gid is not listed in the STORED save’s grantAck. That is the whole definition. There is no server-side “delivered” column, deliberately: the ack lives in the save so that a restore to an earlier point rolls the ack back with the items, and the grant becomes owed again rather than the item vanishing. A server-side ack loses the item silently in exactly that case.

The order of a delivery. (1) The server mints a grant, one row per battle event, keyed drop:<eventId>, holding raw descriptors — lane, grade, tier and the draw seeds. (2) The Worker resolves those descriptors against items.csv on the way out, because the Durable Object may never hold the item table. (3) The client applies the items through invRoomFor, the same guard every other path that hands the player an item uses, and appends the gid to grantAck. (4) The next save carries that ack, and the grant stops being pending. A full bag pauses the drain and reports how many items are still waiting; it never eats them.

grantAck must survive a page load, and until 2026-08-05 it did not. loadRun restores a fixed list of keys from the stored save. grantAck was written to the save and concatenated in two places but was not in that list, so every page load began with an empty ack. The first save afterwards then overwrote the stored history with only what that session had drained, the server was owed every forgotten grant again, and the drain handed the player items they already had. Measured on a seeded account: 40 acks stored, client boots with 0, inventory 28 → 68 within thirty seconds. Live, on real accounts: 134 → 105 → 0 acks across one session, with the save shrinking 64,386 → 62,469 bytes and nothing else changed; another account holding 1,048 grants against 0 acks with a bag at 258 of 160.

The ack has no floor, and that is the sharp edge. A save carrying fewer acks is accepted over a stored save carrying more, and every gid dropped in that write is owed again on the next drain. This is the same class of hole the rollback work closed for maxFloor, playerXp and classXp by making them grow-only — and grantAck is the one field where walking backwards mints items. Re-acking is idempotent and never produces a duplicate grant, which is what makes recovery from a wipe safe.

Failure modes to keep in mind. A grant whose items all fail to resolve is still offered, with an empty item list. The ack list grows with every delivery and is not pruned against the grant lane’s own retention, so acks for long-expired grants stay in the save as dead weight — on a heavy account that is roughly 19 KB against a 184 KB save, under the 256 KiB ceiling but above the 128 KiB warn line. Nothing here accrues offline: a grant is only ever minted by a battle the player actually fought while connected.

The three fields that never travel

advBattles, advChapters and floors are stripped by the client and by the save door — turn logs and floor pools are device data, pools are derived and logs are prose. advArc, the adventure-log archive, joined them on 2026-08-01 after it walked live accounts into the save ceiling. On login the shell splices all four back onto the adopted server copy, gated on the local slot carrying the same steamid and the same generation — an unstamped or foreign local loses its device log once and nothing else. For the first three the server never holds a value, so the splice is uncontested; for advArc the local copy wins outright, because a stored save written before the strip still carries an archive and that copy is by definition the stale one.

The save ceiling — 131,072 bytes, and what happens when a save reaches it

POST /api/save strips the device-only fields, then measures what remains. Anything over 131,072 B is refused 413 save too large and flagged save_oversize. A legitimate slim save is well under 60 KB, so the ceiling is headroom, not a budget to spend.

Why this matters, measured on a live account. advArc was added on 2026-07-28 and was never added to the strip list, so it rode every upload. On one player's save it was 68,560 B of 127,115 B — 54%, leaving 3,957 B of headroom. Once an account reaches the cap every save is refused, and the client's serverFlush re-arms only on a network throw: a 413 returns false silently, with no retry and no warning. The player keeps playing, /api/battle keeps crediting the ledger, and the next login adopts the stale stored copy — because the server save is authoritative on login. That is the rollback. One account went thirteen hours and 1,908 credited kills between two accepted saves; three of five active accounts were at or against the cap, and every healthy account was far below it.

The archive lives on the device only. It is spliced back into the adopted save by syncSaves() on login, and for this one field local wins — unlike the three fields above it still exists inside every save written before the strip, and that stored copy is by definition the stale one. A device with no archive of its own keeps the server's last upload rather than nothing. Without the splice, every login would blank the player's log. No migration is needed: the first post-fix save is under the cap, is accepted, and the stored blob sheds its archive on that write.

Diagnosing a stalled account. The admin console's per-player routes read the WorldDO and answer empty, so use the key-gated doors: /api/backup/history?sid=&realm= for the version ring (a version number that has not advanced while play continued is the symptom) and /api/backup/facts?sid= for the ratchet and ledger the server built from credited battles — the only honest record of what a rolled-back player actually earned.

Known and not yet fixed: a refused save is still silent to the player — any non-OK, non-409 answer should warn and pause, since a save being refused is functionally offline. The archive also packs one event per block, so gzip+base64 inflates it (40,912 B of text stored as 68,560 B, against 7,856 B if packed as designed); now that it stays on the device this is a localStorage-quota problem rather than a save-ceiling one. And 275 of 405 archived battle rows carry a blank timestamp.

Design vs build: the table above says the adventure log lives as server rows fetched on demand. It never did — the archive rode the save instead. The server-side log is now specified around what the battle path already knows (player power, result, loot) rather than around uploaded prose, and the client's copy is requested only when there is something to compare.

Inventory — synced every save, validated in the Worker

The bag stays inside the save. On every sync the Worker checks each row against items.csv and creatures.csv and removes anything that could never have existed, then forwards a clean body to the object. It runs in the Worker and not the object for the same reason the drop tables do: items.csv is 208 KB, a save fires every 10–60 s, and handing that table to a Durable Object per request is the cost trap the whole drop design was shaped to avoid.

Eggs have grades, not tiers. items.csv authors them with a blank Tier and the client writes tier: 0. A validator that compared the two would call every egg in the game a mismatch — 60 across the live accounts, 54 on one of them. Untiered bases skip the tier test entirely.

Legality is not provenance. The checks above ask whether an item could exist, which needs no history. Whether a legal item was ever actually granted is a different question, and the server's grant record only begins the day it shipped — so every item every live account holds predates it. Unrecognised items are therefore FLAGGED, never removed, until granted items are born carrying a server-issued id. The server keeps one row per item so it can answer that question later; the first sync adopts what an account already holds, once.

Nothing is stripped silently: every removal is flagged and counted back to the client in srv{}, and the validator fails open — if the codex cannot be read the save still lands untouched.

When the write path dies

There are two writers and only one of them can be latched off. _staleInst (another window took the localStorage slot, or the slot was cleared underneath this one) and _loadBroken (the save would not parse) both stop saveLocal and serverFlush. Neither stops /api/battle. A window in that state keeps being credited — the ledger and the floor ratchet advance normally — while the save blob stands still. On the next login the server copy wins unconditionally, which is correct, and everything that lived only in the blob is gone with it: wallet, inventory, creature levels, eggs, pens.

This cost a player ten hours on 2026-08-01. His last stored save was ver 874 at 10:43 UTC; the next was ver 876 at 21:11 carrying playerXp 478,119 and maxFloor 69 from the server's own ledger and ratchet, beside the Ichor and the 66-item inventory of 10:43. The only warning had been a toast, and a toast does not stop autoplay.

The fence — who owns the save right now

A login already fences other devices: /api/_internal/session deletes every previous token for the steamid, so the old device's next request is simply unauthenticated. It does not fence other tabs, because two tabs share one cookie, one token and one session row — and that is the case that cost ten hours on 2026-08-01.

So the token is per instance, not per login. GET /api/save is the moment a tab adopts the save, so it mints a fresh epoch on the session row and returns it. Every later request from that tab carries x-ht-epoch. The object compares and refuses 409 stale_session on any mismatch, flagging stale_instance. This is Kleppmann's fencing token: the guarantee only exists because the resource rejects the stale number — a client that checks itself is worth nothing once the client is what has failed.

The background flush — a 429 is not a throw

The client pushes on visibilitychange → hidden and on pagehide, both with fetch(…, {keepalive:true}), guarded by _srvDirty so an untouched session sends nothing. Two defects sat on that path, both fixed 2026-08-03.

1. A rate-limited save was dropped silently. serverFlush clears _srvDirty before the fetch, and the .catch() that re-arms it only runs on a network throw. A 429 resolves — it fell through to return !!(r&&r.ok) and nothing re-armed, so the client went on believing it was clean while the write never landed. The save class is cap 10 / 6-per-minute, and this is the one path where the page may not survive to retry. Any non-OK response now re-arms and honours the server's retry_ms.

A 409 is the deliberate exception and must never re-arm. A conflict means this window is stale; resending is precisely the wrong move. It returns through onSaveConflict above, which reboots onto server truth.

2. Backgrounding burned the rate bucket. hidden and pagehide bypassed the debounce, and on a phone hidden fires on every screen-off, notification pull and app switch. Each one spent a token; three breaches inside the window soft-block the account, which is the trap that once made a signed-in account look logged-out for seven hours. hidden is now throttled to one flush per HIDE_COALESCE_MS (15 s, matching the 429 retry_ms); _srvDirty is deliberately left set when a flush is skipped, so nothing is dropped and the debounce heartbeat sends it.

pagehide is never coalesced. Backgrounding is recoverable because the page survives; a close is the last chance there will ever be.

Why not sendBeacon: it cannot set custom headers, so it cannot carry x-ht-epoch. The fence treats a missing epoch against a non-null session epoch as a mismatch, so a beacon write would be refused — and exempting it would reopen the exact bypass the fence exists to close. fetch(keepalive:true) can set headers, which is why it is used.

OPEN, and it interacts with the save ceiling above: a keepalive request body is capped at 64 KB by the Fetch standard, while a save is allowed up to 131,072 bytes. Any save past 64 KB therefore cannot be flushed on unload at all, and the largest accounts are exactly the ones with most to lose. Unverified against the runtime; it needs measuring, and if it holds the unload path needs a smaller payload rather than a bigger allowance.

Client: serverFlush(), HIDE_COALESCE_MS in play/app.js. Probe: tools/probe_saveflush.py (8/8).

The shell adopted server truth into a key the app never read

This is the root cause of the multi-device rollback, and it is two constants that drifted apart.

  • index.html — REALM_KEYS = { standard: 'herumon_run_rel_v1', … }. syncSaves() writes the authoritative server save here on every boot.
  • app.js — runKeyBase() returns herumon_run_v2:<env>:<sid>. loadRunInner() reads this.

The only bridge between them was the legacy migration in app.js, and it is gated on have == null — by design, "a player who already has a namespaced run keeps it and the shared blob is simply dropped." That is correct for a one-time migration and fatal as a permanent bridge: on any device that had played before, the freshly-adopted server save was written to the legacy key, skipped by the migration, and then deleted unread.

Why every other guard was silent. The app then booted on its own stale state holding a legitimately minted epoch and a current base_ver — so by every check the server makes, the write that followed was valid. Proven separately: tools/probe_rollback.py drives a real worker and the server refuses every stale combination there is (old epoch, old base_ver, borrowed epoch, omitted headers). The fence was never the problem. "Server wins on login" was never the problem either — it won, into a slot nothing loads from.

It also explains the damage pattern. playerXp, classXp and maxFloor survived because they are ledger-backed and grow-only server-side, so a stale blob could not lower them. Everything held only in the save — wallet, bag, equipOv (including creature XP), soulOv, sockOv — rolled straight back. And a refresh never healed it, because the migration is skipped on every boot once the namespaced key exists.

Fix: the shell now writes the adopted save to both keys. The legacy slot still feeds the first-boot migration for a device that has never played; the namespaced slot is what loadRunInner opens. The key formula is duplicated in the shell and must stay identical to runKeyBase() — tools/probe_runkey.py is the gate, and its control (empty namespaced key) matters as much as its failure case, because a probe that only shows the bug cannot tell a real defect from a broken harness.

The save cadence is a coalescer, not a heartbeat — and it stops during a fight

queueFlush() is a trailing debounce armed by an action, not a periodic tick: 25 saveRun() call sites arm it, _srvFlushAt keeps the earliest pending deadline, and the rAF heartbeat only checks whether that deadline has passed. An idle, clean session sends nothing. Its own comment states the intent — "10s debounce that resets per action, so a whole loadout rework becomes ONE server row."

Inside a battle that guarantee inverted. State changes every turn, so the save re-dirtied immediately and the coalescer degenerated into a true ten-second heartbeat for the fight's entire duration. Those are the least valuable saves in the game: /api/battle has already credited the ledger server-side, and enterBattle is a hard gate that awaits a flush and refuses the fight if it does not land — so the previous battle is already stored. The client was re-uploading, at full save size, a battle the server already knew about.

And that traffic alone consumed the entire rate budget. A save every ten seconds is 6/minute; the save bucket is cap 10 refilling at exactly 6/minute. Zero headroom — so every one of the seven event-driven flushes (battle-entry, floor-entry, boss-entry, hidden, pagehide, signout, stale-writer) was an overdraft against a 10-token buffer, and three breaches inside ten minutes soft-block the account. That is the mechanism behind an account that looks logged-out while it is signed in.

The fix is to stop ticking while a round is in progress. FIGHT_PHASES is bintro, intro, select, target, confirm, resolving — deliberately narrower than gearBonus's inBattle list, which also contains victory, powerup, evolution and defeat because it answers a different question ("are stats locked"). _srvDirty is left set while suppressed, so the pending flush fires on the first tick after the fight ends. Leaving the fight is therefore the victory flush, for free — no second trigger to keep in step, and victory previously had no flush of its own at all. A close mid-fight is still safe, because pagehide flushes unconditionally.

Measured, not reasoned (tools/probe_flushrate.py, 4/4, counting real POSTs while re-dirtying every 400 ms as a fight does): 0 saves across a 25-second fight, against 2 in the same window on the floor, which is the control proving coalescing still works. The held flush lands on the transition to victory.

Why this rather than lengthening the interval. Tuning 10s to 20s would have halved a number that should be zero. The interval was only long enough to matter because we were saving something the server already had.

Client: queueFlush(), maybeFlush(), FIGHT_PHASES in play/app.js. Probe: tools/probe_flushrate.py.

Codex data loading — the client fails OPEN, the server fails CLOSED

The game's tables (creatures.csv, floors.csv, floor_creature_rarity.csv, moves.csv, items.csv, classes.csv and a dozen more) are fetched from the codex at boot — live main on dev, the immutable DATA_PIN snapshot on release.

The server treats a missing table as fatal: /api/floor/enter answers 503 spawn_data_unavailable rather than build a pool it cannot vouch for — no pool without truth. The client does the opposite. A failed fetch resolves to null, the loader emits Core CSVs missing — game data incomplete, and play continues. Worse, the loader then aborts at its first unguarded dereference of that null (crs.forEach), so every structure it would have built after that point is missing too — the client is left partially initialised, with no single flag saying so.

This is the data side of report #20 (“sumiu td” — the screen vanished). The CSVs were never wrong; they were absent. With no creature table, every spawn descriptor the server sent resolved to nothing and warned Spawn "?" has no Line_ID in creatures.csv. That nameless unit is what threw inside renderVals, and because renderVals is all-or-nothing, one exception blanked every binding on screen at once. Reproduced by blocking exactly one cross-origin CSV: the client boots, is playable, and holds no creature data at all.

Mitigated (2026-08-04): core tables now retry a transient failure — three attempts with backoff, network errors and 5xx only. A 4xx is not retried, because a file legitimately absent from an older DATA_PIN must fail fast rather than stall the boot three times over. Measured: two 503s followed by a success now loads all 300 creature rows with no warning at all, where before a single 503 lost the table for the whole session.

Ruled 2026-08-04 (owner): if it cannot load, it cannot play. When the retries are exhausted the client now fails closed and matches the server. It stays on the loading screen, names the file that did not arrive, and offers RELOAD; save writes are stopped so a half-initialised session can never overwrite real progress. It also files its own bug report with the log attached, because the player cannot describe this failure and the log is the only thing that identifies which file died. One report per boot, and a failure to report never becomes a second error.

Implementation note worth keeping: the halt screen (#__pause, z-index 99991) sits below the loading screen (#__load, z-index 99998). If the boot never finished, the loader is still up and the halt message renders completely invisible underneath it — every computed style reads visible, the text is in the DOM, and the player sees a logo and nothing else. A DOM text assertion passes. This was caught by screenshotting the result, not by querying it. The message is therefore drawn on the loader, which is also the honest behaviour: the game never started, so it never leaves the loading screen.

The battle snapshot — one slot per kind

A battle in progress is held on the device, never on the server: persistBattle() writes {units, round, turns, floorNum, engagedIdx, inBossFight, streak, pvp} plus the seed and the move log into localStorage, and tryResumeBattle() reads it back. The server holds nothing mid-fight — a spawn slot is marked dead only when a kill is credited — so a paused enemy is still standing on the floor when the player comes back.

There are now two slots, named by kind (ON DEV, not yet on release). There was one: herumon_battle_v2:<env>:<sid>, with no kind in it, and persistBattle writes s.pvp into that same blob. A PvP match joined out of a PvE battle therefore overwrote the paused PvE fight. PvE keeps the historic key so a snapshot written by an older build still resumes across the update; PvP is …:<sid>:pvp. The kind is carried by the key and never inferred from the blob — a snapshot is only ever read out of the slot that owns it.

  • Clearing is scoped. clearBattleSave(kind) names one slot, defaulting to the kind of the fight on screen. A PvP defeat must not take the parked PvE fight with it.
  • Wiping is total. Account-level wipes — foreign slot, epoch bump, generation reset, save conflict — go through rmBattleSaves() and clear every slot. A wipe that leaves one snapshot standing is the foreign-slot bug again, one key over.
  • Boot prefers the live match. With both slots populated, resume takes PvP: it has an opponent on a clock, while the PvE fight is static and keeps until it is asked for. The PvE slot is left untouched, which is what makes pause-and-return possible.

And the resume path had never once run. The reconcile guard that drops a foreign or poisoned snapshot called .filter on snap.units — which is an object keyed a0/a1/a2/e0/e1/e2, not an array. It threw on every boot, the surrounding catch called clearBattleSave(), and the snapshot was deleted instead of restored. Measured on the pristine build rather than read: persist a real fight, reload, and the client lands on the floor screen with no resume note and an empty slot. Fixed by iterating the object's values; the same guard's floor test read d.floor and d.floorNum, neither of which exists at the top level of a snapshot, so it evaluated to 0 and never fired either. After the fix a reload returns to select with all six units and the resume note. This is on DEV only; on release, no battle resumes.

The single write path — one facade, one watermark

ON DEV, not yet on release. The save is being split into seven keys by write frequency (run, party, pens, inv, sock, codex, pvp) held in save_parts beside the authoritative saves blob. An audit on 2026-08-04 found that six code paths write saves and exactly one of them wrote the parts — the save door. The five that did not: the ops restore door, the R2 backup restore, bulk dismantle, the ledger-reconcile sweep, and admin rollback. They were found by measuring, not by reading, which is the reason to assume there will one day be a seventh.

Every writer now goes through writeSave(). It writes saves, splits and writes the changed parts, and stamps a watermark, all in one transaction. This is not the dual-write anti-pattern: that anti-pattern is about crossing a transaction boundary between two independent systems, and saves and save_parts are two tables in ONE SQLite database inside ONE single-threaded object. What three separate save platforms advertise as a hard-won feature — atomic writes across records — is free here. (research.html entry 4.)

PieceWhat it guarantees
writeSave(sid, realm, d, ver, ts, raw)The only place saves is written. Splits and stamps in the same transaction. d may be null when a caller holds only a string it could not parse — the save still lands and the watermark is cleared, so the parts are known-stale rather than silently wrong.
save_parts_markOne row per (steamid, realm) recording the saves.ver the parts were last reconciled against, and the wipe generation they belong to.
partsFresh(sid, realm)The stage-3 primitive. Parts are trusted only while the watermark equals saves.ver and the generation still matches. Reported by the parts door now, so the rate is known before anything trusts it.
Monotonic verAn invariant, not a convention. A writer asking for a version at or below the stored one is bumped forward and flagged save_ver_nonmono — otherwise a restore that lowered the version would make stale parts read fresh.

Why both a facade and a watermark, when either alone looks sufficient. The facade is the fix: it makes the five bypassing writers correct. The watermark is what survives the writer nobody remembered — a raw write anywhere leaves the mark behind saves.ver, and the read path rebuilds instead of serving the old projection. A guarantee that depends on remembering to call a function is exactly what just failed.

The watermark is stored, never inferred. writeSaveParts skips any key whose content hash did not move, so max(save_parts.ver) lags saves.ver whenever an accepted save changed nothing in a key. Measured on a live account: saves.ver 3430 against a highest part version of 3429. Inferring the watermark would have read that account as fresh.

A realm reset now clears the parts. resetRealm deleted saves, save_hist, chains, ledger, progress and more — and there was no DELETE FROM save_parts anywhere in the Worker. Inert while saves is authoritative; at read cutover the wiped run would have loaded straight back out of the projection, so the reset would silently not have happened. Both defences are in: the generation stamped on the watermark makes stale parts unreadable, and the rows are deleted as well, because ignoring data is not reclaiming it.

When the battle credit cannot be delivered

ON DEV, not yet on release. The server's figure is the only number a battle pays (see system-xp.html), so the question of what happens when that answer does not arrive stopped being cosmetic. Owner ruling: hold the player for a couple more tries; local authority is never an option; if it is an outage the player gets the reconnecting window, not a fabricated battle end; and a failure files an automatic report.

AnswerWhat happens
Network throw, or 5xxRetried. The request may never have arrived. Three attempts total, backing off 600 ms then 1800 ms with jitter.
429Retried, but never sooner than the server's own retry_ms. Retrying inside the window is what turns a rate limit into a soft block, and a soft block on an honest player is how the seven-hour login incident happened.
Any other 4xxNot retried. A 400/403/409 is a decision, not an outage; hammering it spends the bucket and files an honest player into the traffic table. The body still heals the floor pool exactly as before.
All attempts exhaustedThat is the outage. Play pauses into the reconnecting window, nothing is credited, nothing is banked, and one automatic report is filed.

Retrying is safe by construction, and it was checked rather than assumed. /api/battle is deduplicated on the battle event id, so a repeat credits once.

But the dedup branch used to answer nothing, and that was a hole the moment the client stopped crediting itself. It returned {ok, dedup} with no figures, so a retry after a lost response — the request landed, the answer did not — paid the player zero for a battle the server really had credited. The event row now stores the answer it gave and the dedup branch replays it. It costs nothing extra: the credited figures are all known where the row is already written, and rows written is most of the bill. Drops are deliberately not replayed inline — they were minted into the pending lane, and draining that lane exactly once is the whole point of it. Events recorded before this shipped have no stored answer and replay as a bare dedup, which is the old behaviour rather than a new hole.

An exhausted credit pauses immediately, and does not wait for the poll. The connection check normally requires two consecutive misses — one blip is not an outage. A caller that has already failed three attempts with backoff has proved the point far better than one poll miss, so it asks to pause at once. Waiting for a second miss let the player fight another battle that could not be credited either, which is precisely what “nothing happens offline” forbids. Incidental failures and the 60 s poll keep the two-miss rule.

The report is budgeted and bounded. /api/feedback shares the other rate class with hatching, breeding and the shop catalogue, so during an outage an autoplaying account would otherwise file one report per battle and rate-limit itself — reporting a failure must never become the second failure. Battle-credit failures get two reports per session with a sixty-second cooldown; the boot bucket keeps its separate one-per-boot budget. The log payload is capped per line, truncated to the last 16 KB (the failure is at the end, not the start) and stripped of C0 control bytes. That is a size and hygiene bound, not a security boundary: a report is text a browser wrote, and whatever reads it must still treat it as untrusted and never interpolate it as markup.

The battle chain, and why it kept “breaking”

ON DEV, not yet on release. Every battle event carries the chain it belongs to and the head it follows — a hash of the previous event. The server compares the submitted head against the one it holds and flags chain_break on a mismatch. The flag fired 19 times on the owner's own account, which is exactly why it was never enforced.

The cause was an ordering difference, not an attack. The client advanced its head when it built the event, before the request was sent. The server advances its head only after the event passes validation. Every path that returns before that write therefore left the client one ahead:

  • bad event and bad slot — malformed submissions.
  • dead_slot — the client claims a spawn the server already marked dead, which a legitimately resumed battle can do.
  • spawn_data_unavailable (503) — fail-closed, and what a cold start or a deploy produces.
  • Any request that never landed at all.

It self-corrects after exactly one flag, which is why the pattern looked odd: the mismatching battle still advances the server's head, so the battle after it lines up again. Ten flags on one chain id over a day and a half is ten rejected or lost battles, not a sustained break.

The head now advances on confirmation. An answer without an error — credited, accepted-but-uncredited, or a dedup replay of an event the server already holds — means the server's head is now this event's. An error means it rejected the event and its head did not move, so the client's must not either; the retry and the pause cover the no-answer case, where it also did not move. The two heads now agree by construction.

It is still not enforced, and that is deliberate. Making the flag trustworthy is a separate decision from acting on it. A correction of the record belongs here too: the first diagnosis of this said the server does not advance on an uncredited battle. It does — the chains write is unconditional, and a rate-capped battle advances it. That conclusion came from a probe stub rather than the worker, and the real cause is the list above.

Alt-tabbing must not cost a battle

Two things go wrong at once when the tab is hidden, and only together do they produce COULD NOT REACH THE SERVER — THIS BATTLE WAS NOT COUNTED:

  • visibilitychange→hidden fires serverFlush('hidden',{keepalive:true}). A real save is ~131 KB and gzips to ~24 KB, and keepalive bodies share a 64 KiB browser-wide quota. /api/battle is also keepalive, so a credit in flight competes with the flush for that quota and can be refused by the browser before it ever reaches the network.
  • That refusal is indistinguishable from a network error in the retry, so all three attempts burn inside ~2.4 s while the tab is still hidden, and the run pauses into the reconnecting window.

An attempt made while the document is hidden no longer advances the attempt counter. A hidden tab is not evidence of an outage. A wall-clock bound still applies, so a player who never comes back cannot retry forever, and the three-attempt rule is untouched once the tab is visible — which is the case that rule was written for.

And the two keepalive bodies stop competing at all: the hide flush yields while a credit is in flight. The save is the cheap one to defer — the battle event is the authoritative reward record, and the credit's own success already queues a flush — so the save still lands at the next boundary. Nothing is skipped, only ordered.

Nothing about this banks a result offline. A credit that genuinely cannot be delivered still credits nothing and still pauses play; what changed is that a tab switch is no longer mistaken for that.

Client: the _battlePost retry and the visibilitychange handler in play/app.js. Probe: tools/probe_hidecredit.py — BEFORE 6/6 (asserting the retry has no notion of a hidden tab), AFTER 7/7.

The spawn budget is one pool, and every floor entry re-asks for it

The budget is keyed by realm, not by floor: one pool, 1/min, cap 10, spent wherever you fight. Floors keep their own dead[] so identity and roll serials stay per-floor — only the credit is shared.

  • The server caps the pool it hands out. If the budget is below ten, a floor is shown with only as many spawns as the budget will honour — including a floor never visited before. The pool the client is shown is the pool the server will pay for, so a player can never fight a spawn that will not be credited.
  • The client re-asks on every entry. Once a floor had been fetched it was served from cache forever, so a floor first walked on a full budget kept showing its ten spawns long after the budget drained — measured at 2 credits and 10 spawns shown. One request per floor change, which is a rare path; battles are untouched.
  • A cached pool is capped locally as well. The boss-den exit and the resume path also paint from cache, so the last known budget caps whatever is drawn. Suppression is for display only — the entries are untouched, so identity and serials survive and the next server answer restores them.

Why over-showing is worse than it looks. An over-budget kill is not merely unpaid: the server sets credited = false and raises a spawn_budget flag against the account. A player shown a full map they cannot be paid for therefore accrues anti-cheat signal for doing exactly what the screen invited. Under-showing is self-correcting; over-showing is not.

Travel now requires the server answer for every floor, cached or not. That follows the offline ruling — a dead connection must pause rather than serve stale content — and the existing 30 s FLOOR N UNREACHABLE watchdog covers the failure.
