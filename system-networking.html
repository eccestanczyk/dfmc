NETWORKING ARCHITECTURE

Other Systems › Networking Architecture

How the client and the backend talk, what each side is allowed to decide, and what every call costs. Read this before changing anything in src/worker.js or any code path that makes a network call. The stack is Cloudflare Workers plus SQLite-backed Durable Objects. The older Save, Economy & Anti-Cheat page describes the retired Unity/UGS design and is kept for its doctrine only — its named services no longer apply.

Doctrine

RuleMeaning
Clients send events and requests, never stateThe save is a prediction cache. A server reconciliation overwrites it. Editing it should be inert.
Nothing happens offlineOffline play is banned outright. No queue, no outbox, no banking, no replay of work done while disconnected. On loss of connection autoplay pauses, the battle pauses, and a reconnecting window shows. Play resumes only when the connection returns.
The server derives rewardsThe client reports what it did, never what it earned. XP, food and drops come from server tables, and the client applies what it is told.
Cost scales with battles, not with time connectedAn idle account must write nothing. If a player is doing nothing there is nothing to save.

⚠ Durable Object rules — a 1000× cost risk

Duration is billed in wall-clock time at the full 128 MB allocation whenever an object is active or idle but unable to hibernate. An idle object that qualifies for hibernation is not billed at all. Hibernation requires all of: no setTimeout/setInterval, no in-progress awaited fetch(), no standard WebSocket API, and no request still being processed. It then hibernates after 10s idle.

Nothing inside a Durable Object class may ever use setTimeout, setInterval, a plain WebSocket accept(), or an awaited fetch(). Any one of them makes the object permanently non-hibernateable. With a request arriving every few seconds the object then never leaves the billed idle state.

Throughput ceilings

LimitValueConsequence
Requests per single object~1,000/s soft limitPast it the object queues, then returns an overloaded error to the caller
blockConcurrencyWhile()~200 req/s at 5ms per callBlocks all concurrency unconditionally. Reserve for initialisation and migrations, never regular request handling
SQLite per object10 GBWrites fail with SQLITE_FULL

Cloudflare's own guidance is “do not create a single global Durable Object that handles all requests” — which is exactly what idFromName('main') is today. Their Queues team hit the same wall at ~400 msg/s and only got a 10× speedup by sharding into consumer-shard objects. Shared objects must therefore be sharded too: a single leaderboard object is the same mistake at a smaller scale.

Scheduled work is a Worker scheduled() cron that calls into the object. Never a DO alarm: setAlarm() is itself billed as a row written and keeps the object awake. Also standing: no unqualified DELETE or SELECT in a constructor, and one-off migrations claim their completion flag before doing the work.

The write path — only two writers

There is no periodic autosave. A player sitting in a menu costs nothing.

Forced flush boundaries

A debounce may only ever be pending while the player is fiddling in menus — never while the server is being asked to judge something. Flush immediately on: battle entry, floor entry, boss entry, any purchase, pagehide, and on reconnect. Otherwise the server validates a battle against a stale loadout.

Trust boundary

FactWho decides
What spawned on a floorServer — derived, see below
Whether a battle could be enteredServer — it holds the spawn cursor
XP, food, drops, class XP, creature XPServer — derived from its own tables and returned to the client
Player decisions during a fightClient — the only thing it genuinely owns
Fight simulation — grind and autoplayClient. Guarded by a power-plausibility gate (an unwinnable matchup is refused, not flagged for later review) plus sampled server re-simulation of retained inputs, and cross-player statistical anomaly detection
Fight simulation — ranked, PvP, leaderboard-defining runsServer re-simulates in full. Cheap for turn-based, and only these runs need it
Blanket server-side resolution of every battle is deliberately not planned — extracting the engine into a module both sides import is the largest job on the table. The documented industry line is the split above: full re-simulation for the competitive surface, plausibility gates and sampled auditing for grind. The idle RPG Firestone runs this exact model — 99% server-side with the main battle left client-side because the calculation volume does not justify it — and catches the residual with statistical flagging, reporting roughly 1% of new players banned daily at fewer than 1 wrong call in 500 reports. Note the corollary: flags feed a human queue, they do not auto-ban.

Floor spawns are derived, never stored

ElementRule
IdentityHMAC(serverSecret, account + floor + DATA_PIN + spawnIndex). The secret never leaves the server, so there is no lookahead: a player cannot compute future spawns
RefillLazy on access: min(elapsed_minutes, 10 − current), overflow discarded, frozen at cap. Only spawns whose 60s has already elapsed are ever sent
ConsistencyIndex N always resolves to the same creature, so a spawn keeps its identity and roll until killed, and re-entry never rerolls
Stored{lastAccessTs, liveIndices[], cursor, pin} per floor, ~50 bytes. The save stores nothing about pools
DeliveryFloor entry, and on the /api/battle response. Respawns cost no extra request
Data changesThe pin is stored per floor so live spawns keep their identity; only new indices use the new pin
The server secret is load-bearing. Rotating it rerolls the world for everyone. Treat it like DATA_PIN: set once, never rotated casually.

What the save contains

Out of the saveWhere it lives instead
Battle turn logsNot stored anywhere. Persist {seed, inputs, resultHash} instead and re-simulate to render a replay. This is Supercell's model: replays are not recordings, they recreate the match from where the player tapped, because storing millions of battles as media is untenable. The same record doubles as the audit artifact
Adventure log, chapters and eventsServer rows, written from data the battle endpoint already receives. Fetched on demand, so a new device keeps the record
Floor spawn poolsDerived, see above
Item and equipment display fieldsLooked up from items.csv by id. The save keeps id, quantity and instance data only

Measured against a real save: 655 KB → ~12 KB. Turn logs alone were 68% of it.

Sharding

ObjectHolds
Per-player, idFromName(steamid)Save, ledger, chain cursor, floor cursors, adventure log
SharedLeaderboards, name uniqueness, game-wide rate counters, anomalies — anything inherently cross-player

A single global object caps at ~1,200 players on save size alone, against a 10 GB per-object SQLite limit. Per-player never needs rebalancing; a fixed shard pool does, every time it grows.

Cost model

Rates: DO requests $0.15/M after 1M; duration $12.50/M GB-s after 400k; rows written $1.00/M after 50M; rows read $0.001/M after 25B; SQLite storage 5 GB included. R2 $0.015/GB-month, $4.50/M Class A.

Rows written dominates at every scale, and it is bought down by cadence, not by save size — a row is a row whether it holds 12 KB or 655 KB. Storage size matters for the 10 GB ceiling and for bandwidth, not for this line.

Precedent

Where each decision on this page has been done before, so it is not re-litigated from scratch.

DecisionPrecedent
Rewards server-derived, combat client-sideFirestone (Holyday Studios): 99% server-side, main battle client-side because the calculation volume does not justify moving it. Residual handled by statistical flagging
Replays are inputs + seed, re-simulatedClash of Clans: replays recreate the match from recorded taps rather than storing video, because millions of battles a day would need far too much storage
Server owns the seed; verified leaderboard runsAntGame.io: server generates and controls the seed, the client submits the run, the server re-simulates. Forged submissions are impossible; every leaderboard run is verified
HMAC commit-reveal so the client cannot look aheadThe provably-fair construction: publish the hash of a secret server seed first, compute outcomes as HMAC(server_seed, client_seed:nonce), reveal the seed only afterwards. Works only while the seed stays secret until after resolution
Never expose the seed to the clientDiablo II: Resurrected — a deterministic PRNG with client-visible state was fully reverse-engineered into known-seed farming routes with guaranteed drops
No periodic autosave; event-driven writesNakama's own guidance: avoid background jobs in favour of an event-driven route so work is only performed for players actually present
Offline progression banned outrightOffline income is normally a delta-time calculation against the device clock, and is therefore trivially exploited — Melvor Idle and Territory Idle both have documented clock-skip exploits. Games that keep it either make time server-authoritative or convert offline time into a capped resource spent while online
Economic caps rather than anti-automationIdle players broadly treat auto-clickers as legitimate optimisation, so the defence is the value ceiling per real second — here, the 60 spawns/hour spawner — not client-side automation detection
Staying custom rather than moving to a BaaSPlatforms solve auth, IAP receipt validation, leaderboards and sharded storage; they never solve game-rule validation or anti-cheat. PlayFab cut its free tier in March 2026 from 100,000 to 1,000 lifetime players per title, with the replacement tier limited to studios shipping on Xbox — the lock-in risk in practice
Per-player actor isolationMicrosoft Orleans has run Halo backend services since 2011. The model is proven; a published cost postmortem for a live-service game specifically on Durable Objects does not yet exist, so expect undocumented operational edges
