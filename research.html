1. Durable delivery of server-granted rewards (2026-08-03)

The question. The server decides a battle's drops and returns them inline in the battle response. The client adds them to its inventory and uploads a whole-save blob every 10–20 s. If the save carrying that drop never lands — crash, network loss, a 429, a save over the size ceiling — the item is gone. Does the player get it back on the next sync?

The answer in this build is no, and worse than no: invSync reconciles the server's item table by following the client's save, deleting any uid the save no longer carries. So the next successful sync erases the server's own record that the drop was ever granted. The drops_granted log ages out at 7 days, and there is no re-delivery path anywhere.

What the industry converged on

  • Mailboxes, not inline responses. Rewards are written into a server-side inbox the player explicitly claims. Genshin Impact delivers quest rewards, event prizes, compensation and code redemptions all through Mail, with a 30-day expiry and a 1,000-entry cap that evicts claimed mail oldest-first. Heroic Labs' Hiro ships a "Reward Mailbox" primitive with per-entry create_time, expiry_time, claim_time and a can_claim flag, and states that claims and grants are atomic "to avoid partial updates and double claims".
  • "Exactly-once" does not exist; the target is at-least-once plus idempotent application. The transport guarantees a message arrives at least once and the application makes applying it twice a no-op. The building blocks are a stable idempotency key stored under a unique constraint in the same transaction as the effect, a transactional outbox so the state change and the to-be-delivered record commit together, and consumer-side dedup via a processed-id set or a monotonic high-water mark.
  • Server-authoritative inventory is the norm. PlayFab Economy v2 mutates inventory only through authenticated calls, batchable atomically, each taking an IdempotencyId, with a separate durable transaction history. Steam keeps inventory on Valve's servers and warns that the client-side GenerateItems is "only intended for prototyping". Nakama's docs are explicit: "wallets can only be directly updated from the server to make it more difficult for unintended or exploitative transactions to occur", with an append-only ledger.
  • Destruction is an explicit event, never an inferred absence. Steam has ConsumeItem, PlayFab has SubtractInventoryItems, Nakama appends a negative changeset. Event-sourced designs use tombstones and per-item state machines — granted → delivered → claimed → consumed — so a gap is never read as a deletion.
  • Platform idempotency keys are time-bounded de-dup, not a delivery guarantee. PlayFab enforces IdempotencyId for 14 days and then garbage-collects it, while keeping transaction history for up to four years. Steam's requestid gives at-most-once execution and returns a replayed flag, but documents no retention window and explicitly re-attempts an original that failed. The durable answer to "did this player ever receive grant X" is a pending row or a ledger, never the idempotency key.
  • The war stories are all rollback races or client authority. RuneScape Classic's 2003 partyhat duplication ran to over two million copies and was never rolled back; Old School RuneScape has taken repeated emergency rollbacks (Sins of the Father in 2020 corrupted equipped/inventory save state; Guardians of the Rift in 2022 forced a shutdown twenty minutes after release). Minecraft-family dupes are theorised the same way — "the game saves one state without properly removing or updating another", which is structurally identical to a whole-save-blob race.

The finding that matters

This build already has all three primitives the industry answer is made of, and they are simply not wired together:

  • a durable pending queue with idempotent claim (the grant lane),
  • a server-side per-instance item record (the items table, completed 2026-08-03 with xp, mut, g, extra),
  • and an explicit consume event — the dismantle claim (_dismQ), where the client says what it destroyed and the server verifies each row against its own previous save before honouring it.

The dismantle claim is the important one, because it is the first place in this codebase where destruction is a positive statement rather than an inferred absence. Generalising that shape to every removal path is what resolves the ambiguity: an item gone with a consume event was destroyed; an item gone without one, still sitting unclaimed in pending, was never received.

Recommended sequence

  • Stage 1 — stop erasing evidence. Remove the set-difference deletion in invSync: never drop a server item row merely because a uid is absent from an incoming save. Extend drops_granted retention from 7 days toward the 14–30 day window the industry uses. Both are small and neither changes player-facing behaviour.
  • Stage 2 — put drops through the lane that already works. Mint each battle's drops into the pending queue (one row per battle, not per item) instead of returning them inline, and move the ack server-side so exactly-once stops depending on save durability. This is what makes a lost save self-healing, and it retires the manual compensation grants that P8-class tickets currently need.
  • Stage 3 — make the save a projection, not the authority. Record every removal as an explicit consume event, reconcile by replaying events rather than diffing sets, and let the client upload intents the server validates. This is the same direction as the server-side inventory ruling and the two should land together.

Cost, because it is the usual objection. Durable Object SQLite bills rows written at $1 per million against a 50-million monthly inclusion, and rows read a thousand times cheaper — and an indexed column adds a second billed row per write. One pending row per battle at 30 battles/hour is affordable, and coalescing a battle's drops into a single row plus batching currency into a ledger keeps it that way. Keep the hot pending table minimally indexed. Revisit if grant writes approach the monthly inclusion.

What would change this. If the save could be made transactional and rollback-proof, inline delivery would be tolerable — it cannot be, over a browser on a phone. If drop volume were a handful per session, a per-grant mailbox row would beat a cursor for flexibility.

Stage 1 shipped (2026-08-03, on dev)

  • The set-difference deletion is gone. invSync no longer deletes a server item row because its uid is absent from the incoming save; it writes a gone timestamp instead. The row is kept for 30 days and pruned after. This does not yet decide why an item left — it stops us destroying the ability to ask.
  • A returning uid is un-tombstoned and keeps its provenance. An item that leaves and comes back (equipped, penned, traded through) clears gone on the next sync via the same ON CONFLICT update, and its origin survives untouched.
  • Tombstones are readable. GET /api/backup/inv now returns rows (live) and tombs (what the account used to hold, newest first). That second list is the point of not deleting — it is the only way to answer "was this granted and then lost?" after the fact.
  • drops_granted retention 7 → 30 days. Not an imported number: hatches already prunes at 30, so 7 was the outlier, and the drop log is the only record of a lost drop.

Still outstanding from the sequence: Stage 2, minting drops into the pending lane and moving the ack server-side, and Stage 3, making the save a projection rather than the authority.

Stage 2 shipped (2026-08-03, on dev) — with one correction to the plan above

The recommendation to "move the ack server-side" was wrong for this architecture, and I did not implement it. pendingGrants already defines pending as minted, not revoked, and not listed in the STORED save's grantAck — so the ack is only believed once the save containing it has actually landed. Moving it into a server table would make things worse: the server would mark a grant delivered before the save carrying it was durable, which is precisely the failure being fixed. The ack living in the same atomic unit as the item is the property that makes rollback self-healing, and it is a design, not an accident.

  • A battle's drops are now minted into the pending lane, keyed on the battle event id (drop:<eventId>) — one grant per battle, coalescing all of that battle's drops into a single row, as the cost note recommends.
  • The inline copy still rides the response, so the victory screen is unchanged and D's timing ruling stands: chance-bearing grants arrive during the vicBar window rather than on a later drain.
  • The client acks the same gid it just applied. The two are ONE delivery, not two: if the save lands the grant is never pending; if it never lands the ack is lost with it and the next boot drains the same items exactly once. The gid is the identity that makes double application impossible in either direction. The mint and the ack must never ship apart — minting alone would re-deliver every battle forever.
  • Raw descriptors are stored, and named on the way out. The object may never hold items.csv, so the Worker resolves at drain time. That keeps the cost on the rare path — a lost save — instead of adding a round trip to every battle that drops something.

Verified (tools/probe_droplane.py, 5/5): a raw descriptor minted as {lane:'gear', tier:1, grade:'Worn'} is offered while unacked, comes back resolved as a real item row (Crude Signet, ITM-0181), and disappears from pending once an ack reaches the stored save.

Now verified, and the earlier claim here was wrong. This paragraph previously said the mint-on-battle leg could not be tested because the chance tables would not load locally. Both halves of that were false. The tables load fine; the real cause was that the harness fired every battle on ONE chain, which drains its bank — and once a battle is uncredited, drops never roll, because the roll lives inside the credited branch. One chain per battle and it drops on the first try: Faded Rune of Aegis, Rough Garnet, each returning both the resolved drop and its dropGid, and each showing up as pending until acked. probe_droplane is now 8/8 including the battle leg itself.

How the correction was found is the point. rollDrops records exactly why it declined — flag('drop_data', note) — and until today nothing in this system could read a flag. 60 flag() call sites across 57 distinct kinds had been writing to the anomalies table since it was created, and FROM anomalies appeared zero times in the worker. Every guard recorded its reason and then discarded it, which is why a production question had to be answered by reasoning about source — the thing the standing rule forbids and could not actually satisfy. A read door (GET /api/backup/flags, with a kind histogram) was added, and it answered the question on first use: the flags said rate_cap, then spawn_budget, and never once said drop_data.
