1. Durable delivery of server-granted rewards (2026-08-03)

The question. The server decides a battle's drops and returns them inline in the battle response. The client adds them to its inventory and uploads a whole-save blob every 10–20 s. If the save carrying that drop never lands — crash, network loss, a 429, a save over the size ceiling — the item is gone. Does the player get it back on the next sync?

The answer in this build is no, and worse than no: invSync reconciles the server's item table by following the client's save, deleting any uid the save no longer carries. So the next successful sync erases the server's own record that the drop was ever granted. The drops_granted log ages out at 7 days, and there is no re-delivery path anywhere.

What the industry converged on

  • Mailboxes, not inline responses. Rewards are written into a server-side inbox the player explicitly claims. Genshin Impact delivers quest rewards, event prizes, compensation and code redemptions all through Mail, with a 30-day expiry and a 1,000-entry cap that evicts claimed mail oldest-first. Heroic Labs' Hiro ships a "Reward Mailbox" primitive with per-entry create_time, expiry_time, claim_time and a can_claim flag, and states that claims and grants are atomic "to avoid partial updates and double claims".
  • "Exactly-once" does not exist; the target is at-least-once plus idempotent application. The transport guarantees a message arrives at least once and the application makes applying it twice a no-op. The building blocks are a stable idempotency key stored under a unique constraint in the same transaction as the effect, a transactional outbox so the state change and the to-be-delivered record commit together, and consumer-side dedup via a processed-id set or a monotonic high-water mark.
  • Server-authoritative inventory is the norm. PlayFab Economy v2 mutates inventory only through authenticated calls, batchable atomically, each taking an IdempotencyId, with a separate durable transaction history. Steam keeps inventory on Valve's servers and warns that the client-side GenerateItems is "only intended for prototyping". Nakama's docs are explicit: "wallets can only be directly updated from the server to make it more difficult for unintended or exploitative transactions to occur", with an append-only ledger.
  • Destruction is an explicit event, never an inferred absence. Steam has ConsumeItem, PlayFab has SubtractInventoryItems, Nakama appends a negative changeset. Event-sourced designs use tombstones and per-item state machines — granted → delivered → claimed → consumed — so a gap is never read as a deletion.
  • Platform idempotency keys are time-bounded de-dup, not a delivery guarantee. PlayFab enforces IdempotencyId for 14 days and then garbage-collects it, while keeping transaction history for up to four years. Steam's requestid gives at-most-once execution and returns a replayed flag, but documents no retention window and explicitly re-attempts an original that failed. The durable answer to "did this player ever receive grant X" is a pending row or a ledger, never the idempotency key.
  • The war stories are all rollback races or client authority. RuneScape Classic's 2003 partyhat duplication ran to over two million copies and was never rolled back; Old School RuneScape has taken repeated emergency rollbacks (Sins of the Father in 2020 corrupted equipped/inventory save state; Guardians of the Rift in 2022 forced a shutdown twenty minutes after release). Minecraft-family dupes are theorised the same way — "the game saves one state without properly removing or updating another", which is structurally identical to a whole-save-blob race.

The finding that matters

This build already has all three primitives the industry answer is made of, and they are simply not wired together:

  • a durable pending queue with idempotent claim (the grant lane),
  • a server-side per-instance item record (the items table, completed 2026-08-03 with xp, mut, g, extra),
  • and an explicit consume event — the dismantle claim (_dismQ), where the client says what it destroyed and the server verifies each row against its own previous save before honouring it.

The dismantle claim is the important one, because it is the first place in this codebase where destruction is a positive statement rather than an inferred absence. Generalising that shape to every removal path is what resolves the ambiguity: an item gone with a consume event was destroyed; an item gone without one, still sitting unclaimed in pending, was never received.

Recommended sequence

  • Stage 1 — stop erasing evidence. Remove the set-difference deletion in invSync: never drop a server item row merely because a uid is absent from an incoming save. Extend drops_granted retention from 7 days toward the 14–30 day window the industry uses. Both are small and neither changes player-facing behaviour.
  • Stage 2 — put drops through the lane that already works. Mint each battle's drops into the pending queue (one row per battle, not per item) instead of returning them inline, and move the ack server-side so exactly-once stops depending on save durability. This is what makes a lost save self-healing, and it retires the manual compensation grants that P8-class tickets currently need.
  • Stage 3 — make the save a projection, not the authority. Record every removal as an explicit consume event, reconcile by replaying events rather than diffing sets, and let the client upload intents the server validates. This is the same direction as the server-side inventory ruling and the two should land together.

Cost, because it is the usual objection. Durable Object SQLite bills rows written at $1 per million against a 50-million monthly inclusion, and rows read a thousand times cheaper — and an indexed column adds a second billed row per write. One pending row per battle at 30 battles/hour is affordable, and coalescing a battle's drops into a single row plus batching currency into a ledger keeps it that way. Keep the hot pending table minimally indexed. Revisit if grant writes approach the monthly inclusion.

What would change this. If the save could be made transactional and rollback-proof, inline delivery would be tolerable — it cannot be, over a browser on a phone. If drop volume were a handful per session, a per-grant mailbox row would beat a cursor for flexibility.

Stage 1 shipped (2026-08-03, on dev)

  • The set-difference deletion is gone. invSync no longer deletes a server item row because its uid is absent from the incoming save; it writes a gone timestamp instead. The row is kept for 30 days and pruned after. This does not yet decide why an item left — it stops us destroying the ability to ask.
  • A returning uid is un-tombstoned and keeps its provenance. An item that leaves and comes back (equipped, penned, traded through) clears gone on the next sync via the same ON CONFLICT update, and its origin survives untouched.
  • Tombstones are readable. GET /api/backup/inv now returns rows (live) and tombs (what the account used to hold, newest first). That second list is the point of not deleting — it is the only way to answer "was this granted and then lost?" after the fact.
  • drops_granted retention 7 → 30 days. Not an imported number: hatches already prunes at 30, so 7 was the outlier, and the drop log is the only record of a lost drop.

Still outstanding from the sequence: Stage 2, minting drops into the pending lane and moving the ack server-side, and Stage 3, making the save a projection rather than the authority.

Stage 2 shipped (2026-08-03, on dev) — with one correction to the plan above

The recommendation to "move the ack server-side" was wrong for this architecture, and I did not implement it. pendingGrants already defines pending as minted, not revoked, and not listed in the STORED save's grantAck — so the ack is only believed once the save containing it has actually landed. Moving it into a server table would make things worse: the server would mark a grant delivered before the save carrying it was durable, which is precisely the failure being fixed. The ack living in the same atomic unit as the item is the property that makes rollback self-healing, and it is a design, not an accident.

  • A battle's drops are now minted into the pending lane, keyed on the battle event id (drop:<eventId>) — one grant per battle, coalescing all of that battle's drops into a single row, as the cost note recommends.
  • The inline copy still rides the response, so the victory screen is unchanged and D's timing ruling stands: chance-bearing grants arrive during the vicBar window rather than on a later drain.
  • The client acks the same gid it just applied. The two are ONE delivery, not two: if the save lands the grant is never pending; if it never lands the ack is lost with it and the next boot drains the same items exactly once. The gid is the identity that makes double application impossible in either direction. The mint and the ack must never ship apart — minting alone would re-deliver every battle forever.
  • Raw descriptors are stored, and named on the way out. The object may never hold items.csv, so the Worker resolves at drain time. That keeps the cost on the rare path — a lost save — instead of adding a round trip to every battle that drops something.

Verified (tools/probe_droplane.py, 5/5): a raw descriptor minted as {lane:'gear', tier:1, grade:'Worn'} is offered while unacked, comes back resolved as a real item row (Crude Signet, ITM-0181), and disappears from pending once an ack reaches the stored save.

Now verified, and the earlier claim here was wrong. This paragraph previously said the mint-on-battle leg could not be tested because the chance tables would not load locally. Both halves of that were false. The tables load fine; the real cause was that the harness fired every battle on ONE chain, which drains its bank — and once a battle is uncredited, drops never roll, because the roll lives inside the credited branch. One chain per battle and it drops on the first try: Faded Rune of Aegis, Rough Garnet, each returning both the resolved drop and its dropGid, and each showing up as pending until acked. probe_droplane is now 8/8 including the battle leg itself.

How the correction was found is the point. rollDrops records exactly why it declined — flag('drop_data', note) — and until today nothing in this system could read a flag. 60 flag() call sites across 57 distinct kinds had been writing to the anomalies table since it was created, and FROM anomalies appeared zero times in the worker. Every guard recorded its reason and then discarded it, which is why a production question had to be answered by reasoning about source — the thing the standing rule forbids and could not actually satisfy. A read door (GET /api/backup/flags, with a kind histogram) was added, and it answered the question on first use: the flags said rate_cap, then spawn_budget, and never once said drop_data.

2. Save size and synchronisation (2026-08-03)

The question. The client holds the whole player state as one JSON blob and uploads all of it every 10–20 s. The server refuses anything over a ceiling. Three of four live accounts have crossed that ceiling by playing normally, and one accumulated eight and a half hours of play that never reached the server, because a refused save is silent and the game keeps running happily from the copy in the browser.

What the platforms actually do

  • PlayFab hit this exact wall and did not raise the limit. Their legacy player data was key/value "limited to storing data in key value pairs of strings that are limited to 100K" — essentially our 128 KiB. The answer was Entity Objects: multiple structured JSON objects per entity, plus Files for bulk, built to "support larger, more complex data" and to "support atomic updates and concurrency control".
  • Unity Cloud Save does not use a blob at all. A value is limited to 5 MB across all default access-level slots, and the saved state to 2000 keys per access class. Key/value, written per key.
  • Steam Cloud is a different shape and not a fair comparison — developer-set quota, commonly ~1 GB per user per game, 100 MB maximum per write call — because it syncs files at session boundaries, not every ten seconds.

The pattern: nobody stores mutable player state as one blob under one limit. Everyone shards it, and that single decision solves three things at once — you write only the key that changed, so deltas stop being a problem to solve; growth never meets a single wall; and the total budget is far larger anyway.

Measured on this game, not assumed

Compression: measured, and better than expected

Taken on the real save rather than from published ratios:

  • 131,147 B raw → 24,305 B gzipped (5.4×).
  • CORRECTION, same day, before anything was built on it. This entry first claimed compression "fixes both walls today". It fixes one. The 413 measures JSON.stringify(d).length — the parsed object — so compressing the transit body does not move the ceiling at all. Nor can it be applied at rest: six call sites run json_extract(data, …) straight against the stored save (grantAck, invCap, soulCap, maxFloor, heroName, _ledB), and those exist specifically to avoid parsing a 128 KB blob on hot paths. A compressed BLOB breaks all six.
  • What compression genuinely fixes is the 64 KiB browser keepalive cap, which is a wire-size limit — so the page-close flush, which currently cannot send at all for large accounts, starts working. That is worth having, but it is not the lockout.
  • Making the ceiling measure the compressed size would be worse than useless: a client could then ship a 5 MB save that happens to compress well, and the ceiling exists to bound what the server stores and parses, not what crosses the wire.
  • It is not merely a delay, because the collection is capped by design: 160 items + 600 souls = 760 rows. A maxed collection projects to 369,118 B raw → 66,690 B gzipped. The save therefore has a maximum size, and compressed it stays under the ceiling we already had.
  • Both halves are native: CompressionStream in the browser, DecompressionStream in the Worker.
  • Splitting and compressing are complementary, not alternatives. Compression fixes SIZE, which is the lockout. Splitting fixes WRITE VOLUME — a battle write drops from 24,305 B to 2,222 B gzipped, an eleven-fold cut in traffic per battle.

Recommended order

  • 1. Split the save by write frequency into the six keys above. This is the one that fixes the lockout, and it fixes it by construction: once the inventory is its own record, no single key is anywhere near a limit, and the ceiling stops being a thing players can reach. It is the same shape PlayFab and Unity arrived at. Our Durable Object gives atomically what PlayFab had to engineer: several keys in one SQL transaction, so a dismantle that removes a row and adds currency cannot half-land.
  • 2. Compress the payload — for the unload path, not the ceiling. It makes the page-close flush possible again for large accounts and cuts egress; it does not and cannot raise the limit.
  • 3. Move the collection server-authoritative ("local << server"), at which point the client stops holding it at all.

The provenance block stays. It is 33.5% of the save and the obvious thing to cut, and it must not be: the save carries a rich birth record {src, ts, egg{name,grade,uid}, parents, pen, floor} while the server's items.origin holds only the string 'seed'. Stripping it would destroy every creature's origin permanently. Compression makes cutting it unnecessary anyway.

3. Single-writer save ownership and stale-writer rejection (2026-08-01)

Backfilled 2026-08-04. This read was done on 2026-08-01 during the cross-device rollback investigation and was recorded only in OPS.md, which is a task list. It belongs here, because the fence that ships today rests on it.

The question. A player's second device, or a long-open tab, was overwriting newer server state with months-old progress and the save door accepted it. What do shipped save services do when a stale writer arrives?

What the industry converged on

  • Every one of them rejects; none of them silently clamp. PlayFab Economy v2 returns an ETag on read and refuses a mismatched write with 412. Unity Cloud Save issues a WriteLock token per item and errors when it no longer matches — and documents that a null lock skips validation entirely and overwrites, which was precisely the behaviour of our own door. Nakama versions each storage object and rejects on mismatch. DynamoDB uses a condition expression and fails the write. R2 has conditional onlyIf/ETag. Google Play Games hands the app both conflicting snapshots and offers a highest-progress resolution policy rather than picking silently.
  • Nobody orders writes by client wall-clock. Timestamps record when a browser last wrote, not how far the save got, so the device opened last wins by being opened last. Aphyr's treatment of timestamps as unsafe ordering constructs is the standard citation.
  • Earned progress is modelled as grow-only. Max-merge counters (G-Counter shape) are the conventional answer for anything a player has earned, because a merge can then never move a player backwards regardless of which copy arrives.
  • Single-writer leasing is normal in always-online games. The losing session is made read-only and told so — the “logged in elsewhere” message — rather than being allowed to flush.

Where Herumon Tower differs, and it is now a decision rather than a defect. The save door originally stored the client body verbatim, with only two refusals (an older client ts, and playerXp below half of the previous value), and the ratchet clamp rewrote the save downward and answered 200 — a silent rollback by construction. What shipped instead follows the research directly: base_ver optimistic concurrency answering 409 with the authoritative copy; a per-instance epoch minted at GET /api/save and required on every later request, because two tabs share one cookie and one session row and only an instance-scoped token separates them; Web Locks tab ownership so a losing tab never claims the epoch at all; and grow-only treatment for maxFloor, playerXp and classXp. One gap is recorded rather than closed: base_ver proves the client read the latest version, not that its content derives from it.

4. Keeping a split save consistent when many paths write it (2026-08-04)

The question. Entry 2 concluded the save should be split by write frequency, and the split is now built as far as a dual write: save_parts holds seven keys beside the authoritative saves blob. An audit then found that six code paths write saves and exactly one of them writes the parts — the save door. The bypassing five are the ops restore door, the R2 backup restore, bulk dismantle, the ledger-reconcile sweep and admin rollback. Worse, resetRealm deletes saves, save_hist, chains, ledger, progress and more, and there is no DELETE FROM save_parts anywhere in the Worker. So: do we make all five writers dual-write, or do we treat the parts as derived?

What the platforms actually do

  • Independently versioned keyed records, everywhere. PlayFab Entity Objects carry a ProfileVersion; Unity Cloud Save gives every key its own WriteLock; Nakama versions each storage object. The record, not the account, is the unit of concurrency.
  • Cross-record atomicity is the advertised hard part. PlayFab sells atomic multi-object SetObjects as an improvement over its old model, where a partial failure left data inconsistent with no way to tell which key failed. Unity's batch set is all-or-nothing. Nakama offers cross-object transactions only through a specific server-runtime call. Firestore caps an atomic batch at 500 documents. Three vendors treat as a headline feature the thing we get for nothing.
  • Splitting by write frequency is first-party advice, not just our inference. Steamworks recommends separate files for state that changes often and state that does not, so the unchanged part is not re-uploaded every session. That is entry 2's conclusion, arrived at independently and then confirmed.
  • Size-driven splits look the same. CloudKit caps a record at 1 MB and spills the overflow into assets automatically; Firestore's 1 MB document limit plus its lack of partial document reads pushes the same hot/cold separation for cost reasons.

The dual-write anti-pattern, and why it does not apply here

Kleppmann's 2015 articulation is the canonical one: application code updating two independent systems — a database and a search index, a database and a cache — works at first and then desynchronises, because partial failure and reordering have nowhere to be resolved. The prescribed fixes are a single ordered log or change data capture. The transactional outbox pattern is the practical form, and the reason it works states the boundary exactly: the business table and the outbox table are in the same database, so both writes ride one ACID transaction. The anti-pattern is about crossing a transaction boundary between two systems.

We do not cross one. saves and save_parts are two tables in one SQLite database inside one Durable Object, which is single-threaded and whose storage is transactional and serializable. Writing both in one transaction is not a dual write in Kleppmann's sense — it is what the outbox pattern deliberately engineers. So the objection that would normally rule out “make every writer write both” does not apply to us. What remains is not a consistency problem but a coverage problem: six call sites, one of which is correct.

Staleness detection, and admin write paths

  • A monotonic source version compared against a stored watermark is the conventional staleness test. BigQuery exposes a refresh watermark per materialised view; Oracle models freshness as fresh/stale/unusable against its master tables; PostgreSQL requires an explicit refresh and offers a concurrent form so readers never see a torn rebuild. SQLite has no materialised views at all, so the watermark is ours to implement.
  • Mark-stale-then-rebuild-on-read is the standard cheap invalidation. CQRS practice treats a read model as a disposable cache that is dropped and rebuilt, and warns against replaying into a live read model rather than a shadow one.
  • Admin and repair tooling must not be a back door. The rule is stated plainly in general engineering: a business rule expressed only in application code is only in force when that code path runs. Google's SRE data-integrity chapter is the strongest evidence for our specific risk — across nineteen Google recovery efforts the most common user-visible loss came from software bugs deleting data or breaking referential integrity, the worst variants surfacing weeks to months later, and restores across several uncoordinated datastores force engineers to reconcile restored-versus-live in every combination. Our R2 restore is exactly that shape: it would restore the monolith and leave the parts as they were.
  • Deleting across split records needs generation invalidation and real deletion. Erasure practice treats a logical tombstone as insufficient, and the streaming world names the failure mode directly: consumers that replay without applying tombstones resurrect deleted data. Our wipe generation is the right primitive; it is simply not applied to save_parts.
  • Live monolith-to-split migrations are expand/contract plus shadow comparison, promoted only once the match rate holds near perfect over a representative window, and with a decommission deadline for the old path so it is not kept on life support.

Where Herumon Tower differs

  • Decision, and a favourable one: one transactional store per player means we can have cross-key atomicity that PlayFab, Unity and Nakama each had to build deliberately. The five-stage migration already matches expand/contract.
  • Defect: six writers, one compliant. This is the documented admin-back-door failure class, and it was found by measuring rather than reading — which is the reason to assume there will be a seventh writer.
  • Defect, and the sharper one: a realm reset does not clear save_parts. Today that is inert because saves is authoritative. At read cutover it resurrects the deleted run — the reset silently does not happen.
  • Measured, and it kills the cheap version of the fix: the watermark cannot be inferred from max(parts.ver), because writeSaveParts only rewrites rows whose content hash moved. On a live account saves.ver read 3430 while the highest part version read 3429. The watermark has to be stored explicitly.

What this changes about the plan. The two shapes are not alternatives — the correct build is both: a single internal write function that every writer calls, updating saves and save_parts in one transaction and stamping the watermark; plus a load path that trusts the parts only while the watermark equals saves.ver and rebuilds from the monolith when it does not. The facade is the fix; the watermark is what survives the writer nobody remembered. Two invariants come with it: saves.ver must be monotonic across every writer, or a restore that lowers it passes the check silently; and the reset must both bump the generation and delete the parts.

And stage 5 changes what the watermark means, which is worth stating now. A projection-with-fallback design assumes an authority that will eventually stop existing. Through stages 1–4 the monolith stays authoritative and the watermark answers “are the parts stale?”. When the monolith is retired the parts become the system of record and the per-key version becomes an optimistic-concurrency token for the client's per-key upload — which is exactly the PlayFab / Unity / Nakama model. That is a deliberate semantic flip, not a deletion.

5. How games write patch notes (2026-08-04)

The question. Two releases shipped in one day and the Discord notice was written for one of them and forgotten for the other; two of five changes reached release with no codex entry. The failure was not knowing what to write — it was that writing it was an afterthought rather than a step.

The Path of Exile article, and it is a real primary source

“How Patch Notes Get Made”, Path of Exile forum, 28 December 2020, written by Nick, GGG's senior Narrative Designer. Its central point is the one that matters most here: patch notes are not generated from commits. A human reads roughly twenty thousand commits per expansion, keeps only what a player would notice, traces each one back to its work item to find out what it actually means, and then goes into the game and reads every before/after number by hand — the step he says he dreads, because it is the one where things get missed. Finished notes run 7,000–14,000 words and take about eighty hours.

  • Commit notes are written for developers and are useless to players. “Tweaked the damage” tells a player nothing. Translation is the craft, and it cannot be automated.
  • Most work is deliberately not noted. Performance, audio and internal tidying stay out.
  • The notes will be wrong on publication and players will find it. He corrects live rather than pretending otherwise.

What the rest of the industry converges on

  • League of Legends pairs every balance change with a one-line reason above the numbers. The reason defuses far more anger than the number causes.
  • Deep Rock Galactic headers a nerf as a NERF, in a consistent in-fiction voice.
  • Factorio splits the channels: a dry exhaustive changelog for what, a dev blog for why, so the changelog stays scannable.
  • Dwarf Fortress shows that specificity is the comedy. The humour is a by-product of writing the strange true detail, not of adding jokes.
  • Old School RuneScape polls design questions — but Jagex itself warned polls “offer an illusion of choice” when the thing is already built. Poll open questions only.

Why this matters more here than for most games

Herumon Tower is competitive with leaderboards, and players measure. The documented incidents are all about omission, not about the change itself: Destiny 2's Edge of Fate undocumented nerfs, where Bungie's community lead answered “we would be completely out of our minds if we thought we could slip something under the rug”; and Helldivers 2, where a fire-buildup value moved from 2.0 to 2.1 undocumented and the community found it by testing — the studio's own explanation was that small balance changes were not being collated properly. A missing line in a leaderboard game is indistinguishable from cheating. Even GGG has been caught by this: PoE2's 0.2.0 withheld exact numbers, players read it as hiding nerfs, and a game director conceded there were blatant mistakes.

Crediting the player who found it

Accepted practice, and it pays for itself: name the reporter, with permission. Riot does it in Valorant notes. The reasoning is that players who see their report land keep reporting, and players who report into a void stop. With eleven alpha players the rule needs to be consistent or it reads as favouritism — first clear reproducible report gets the credit line.

Where Herumon Tower already agrees, and where it did not

  • Agrees: `changelog.json` already splits `player` from `dev`, which is the audience split the whole field recommends. The release gate already refuses an undated or unreleased entry, and already counts player lines against player-visible commits.
  • Did not: nothing forced the Discord post, and nothing forced a codex entry. Both were habits, and habits fail at the end of a long session. They are now steps in the release gate's checklist rather than things to remember.
  • Did not: player lines were being written at release time from the commit log — exactly the reconstruction problem Nick describes at twenty-thousand-commit scale. The line now gets written at the moment the change is made.

6. Attributing write cost to the system that caused it (2026-08-05)

The question. A Cloudflare spend projection built from measured usage put rows written at 82% of the bill at 100,000 players — $44,072 of a $53,521 month, because Durable Objects charges $1.00 per million rows written against $0.001 per million read, a thousand to one. Nothing in the build records which system produces those rows. The billing telemetry cannot answer it either: durableObjectsPeriodicGroups resolves to object and day and no finer, and there is no route dimension anywhere in the dataset.

What the platforms actually do

Nobody writes on every change. The write-behind (write-back) cache is the standard game-backend shape: mutations land in fast in-memory state immediately, queue in an asynchronous buffer, and a worker flushes batched mutations to durable storage on a fixed interval — commonly every 5 to 30 seconds. The stated benefit is not latency but shock absorption: a traffic spike grows the batch instead of the write rate, so the database is never sized for peak.

The write/skip decision is made per event class, not per field. The long-standing MMO rule is to write the events a player would be furious to lose — trades, deaths, level-ups, zone changes — immediately and under a transaction, and to accumulate everything that happens per tick in memory, persisting a snapshot periodically. The test offered is bluntly practical: how loudly will players complain if this is lost. AWS's Games Industry Lens gives the same advice in queue form — ingest into a durable queue and have a consumer insert in batches — and says plainly that this reduces cost because the database no longer has to be scaled to peak write throughput.

Cloudflare's own guidance points the same way, and it is specific to this runtime. The Rules of Durable Objects guide names in-memory state as the tool for batching and aggregating before persisting, and warns that in-memory state is lost on hibernation, so anything needed later must reach storage first. It also says the runtime already coalesces writes behind output gates, and that blockConcurrencyWhile() on every request is an anti-pattern — at ~5 ms per call it caps a single object near 200 requests per second. Indexes are called out as a deliberate trade: faster reads, slightly slower writes, and on SQLite-backed objects an indexed column adds a second written row per write, one for the table and one for the index.

Attribution itself is treated as a tracing problem, not a storage problem. The current practice is a request-scoped span carrying attributes, with child work inheriting the parent's context automatically, so one tag at the top of a request covers everything beneath it. The FinOps community's “cost per feature” work is explicitly this: combine cloud billing data with distributed tracing to attribute spend at the feature level across asynchronous service chains, and adjust statistically for sampling. Two design rules travel with it — attributes are near-free where the backend bills per event rather than per attribute, so accumulate onto one span rather than creating many; and keep tag cardinality low, because high-cardinality values belong on the span, not on the resource.

Measured on this game, not assumed

  • Storage is entirely SQL: 308 sql.exec call sites, zero storage.list(), no KV facade. 123 of those statements write, across 46 tables — 71 INSERT, 12 UPDATE, 40 DELETE. The widest single target is kv at 18 statements.
  • The live game averages 10.3 rows written and 1,283 rows read per Durable Object request (2026-08-04, 12 active accounts).
  • Rows read per request has gone 57 → 265 → 396 → 370 → 299 → 667 → 1,283 over six days while request volume rose only eightfold. It tracks save size and floor progress, not traffic.
  • A counter already exists and is live: usage(period, kind, n) with an ON CONFLICT … DO UPDATE SET n=n+? upsert, read through the key-gated /api/usage dashboard. It counts two kinds, r2_write and rank_write. The mechanism was built; it was never wired to the write paths.
  • Per-endpoint row cost is measurable today without shipping anything. Running the real worker under workerd locally with sql.exec wrapped — the cursor returns rowsRead and rowsWritten — gave, on an empty account: /api/me 4 read / 0 written; /api/save (GET) 3 / 1; login 3 / 6 across four tables; /api/grants/pending 6 / 9, six of those nine being an automatic bug report writing feedback, flag_rept and anomalies at two rows each.

The finding that matters

A per-write audit trail is paid for in the exact currency it is measuring. One stored row per write doubles the dimension that is 82% of the bill, and the existing helper is worse than a bare insert: spend(kind, n) runs a SELECT on wmeta, a SELECT on usage, then the upsert — two reads and a write per call. Wired into every write path it would add 10–30% to the number under investigation.

The resolution the industry has already reached is that measurement granularity and storage granularity are different decisions. Tag per request, aggregate in memory, and persist per period — one row per system per period, never one row per event. The wrap belongs in one place (the object's constructor) rather than at 123 call sites, because a per-call-site tag misses every statement issued from a helper, and this codebase issues many.

Recommended sequence

  • Diagnose by log, not by table. observability is already enabled in wrangler.jsonc. One console.log per request carrying the system tag and its row totals costs zero database writes and no storage, and a single day of traffic answers the whole question. This is the cheapest correct first step and it is reversible by deleting a line.
  • Then persist, aggregated. For a standing budget dashboard, keep counters in object memory and flush one upsert per system per period, piggybacked on a write the request was already making. Never on a timer: setTimeout/setInterval in the object class are banned outright by the hibernation rule and do_guard fails the build on them, and alarms are flagged.
  • Accept the hibernation loss deliberately. In-memory counters do not survive eviction. For accounting that is acceptable; for forensics it is not, which is another reason the log pass comes first.
  • Capture reads in the same pass. The same cursor carries rowsRead at no extra cost, and reads-per-request is the figure currently climbing.

7. Durable Objects SQLite write accounting, and what it costs to measure it (2026-08-05)

The question. Entry 6 established that rows written is the bill and that attribution needs a tagging layer. This is the mechanics pass: exactly how a row becomes a billed row, what the platform charges to measure itself, and what each lever is actually worth.

How a billed row is counted

  • Cloudflare's documentation is explicit: INSERT, UPDATE and DELETE all contribute, and a statement inserting ten rows bills ten. setAlarm() bills one row written. The key-value methods on a SQLite-backed object store into a hidden SQLite table and bill through the same row accounting.
  • Indexes amplify, and the docs say so: every row update of an index counts as an additional row.
  • Independently measured by Larry Maccherone (lumenize.com, 23 February 2026) — 36 tests reading cursor.rowsWritten under workerd, written because the question kept coming up on the Durable Objects Discord with no experimentally-validated answer. His results:
  • INSERT costs 1 for the row + 1 per index that needs updating.
  • A TEXT PRIMARY KEY without WITHOUT ROWID creates a hidden index, so the INSERT costs 2, not 1. His headline recommendation is to add WITHOUT ROWID to every table with a TEXT or compound primary key — he reports no downside. INTEGER PRIMARY KEY aliases the rowid and costs 1 either way.
  • A compound index (a,b) costs 1 extra write and still serves leftmost-prefix lookups on a; two single-column indexes cost 2.
  • An inline UNIQUE creates a hidden index: +1 per INSERT.
  • UPDATE only rewrites indexes covering columns that changed. Updating one non-indexed column on a three-index table costs 1. This is the cheapest write shape available.
  • INSERT OR REPLACE costs 1 for the row rather than delete-plus-insert, but rewrites all indexes — 4 on a three-index table. A narrow UPDATE beats it.
  • Partial indexes (WHERE status=1) bill only when the written row matches the filter — near-free for sparse flags.
  • DELETE reports rowsWritten 1 regardless of index count. He flags that he could not confirm whether index cleanup is genuinely unbilled or merely not surfaced by the cursor.
  • Column count is irrelevant. A two-column and a ten-column table both cost 1 per row.

The correction this forces on entry 6

Batching does not reduce billed rows. Entry 6 cited AWS write-queueing and Cloudflare's in-memory aggregation approvingly and left the impression that batching lowers the bill. It does not, not directly: a multi-row INSERT … VALUES bills exactly the same total as the same rows inserted one at a time. Batching coalesces the commit — latency, atomicity, output-gate round trips. Billed rows are always rows touched plus index updates. Batching only lowers the bill when it removes redundant row touches: collapsing many per-tick whole-row rewrites into a single flush of the final state. That is dirty-flag coalescing, and it is a different mechanism from a batch INSERT. Stating it loosely will produce a saving that does not arrive.

What the platform charges to measure itself

  • Every counter bump in the SQL usage table is a billed write, permanently. Diagnostic counters added there are a recurring cost, not a one-off.
  • Workers Analytics Engine writeDataPoint() is hibernation-safe. It is fire-and-forget, returns immediately, needs no await and no waitUntil(), and opens no outbound connection — so it is none of the things the Durable Object lifecycle documentation lists as blocking hibernation (an awaited fetch(), the WebSocket API, an outbound TCP or WebSocket connection, an in-progress request, a timer). Checked against that list deliberately, because the hibernation rule is a thousandfold cost difference here.
  • Limits: 20 blobs and 20 doubles and 1 index per data point, 16 KB of blobs, a 96-byte index, 250 writeDataPoint calls per invocation, 3-month retention. Currently unbilled; the announced price is $0.25 per million written and $1.00 per million read, with 10 million written per month free.
  • Cardinality is free — each blob is stored independently, so adding dimensions costs nothing. But sampling is equitable per index value, so index on something low-cardinality (an event kind, a floor bucket) and never on the steamid, or every player becomes their own sparsely-sampled bucket.
  • It is sampled, lossy and best-effort, with no retry and no backpressure. Fine for diagnosis and a budget dashboard; never a system of record for a granted reward. It has also historically returned undefined under local wrangler dev — guard the call.

There is no write cap, and three people have proved it

  • Little Bear Apps, 18 March 2026. Two bugs wrote 4.83 billion rows to D1 in one month on a $5 account, an overage of about $4,868, waived after eighteen days and four escalation channels. One bug was a cron re-processing the same batch with no dedup and no offset tracking — 3.45 billion writes in four days, peaking at 1.42 billion in a single day. The other was an INSERT with no ON CONFLICT re-inserting rows that already existed, roughly 910 million redundant writes. Normal usage for that account was about 200 writes an hour.
  • Their remediation is ours almost line for line: usage tracking moved off the billed store into Analytics Engine; three-sigma anomaly detection on a 168-hour rolling window, which they calculate would have caught the spike in under an hour; monitoring inserts collapsed from about 200 individual writes an hour to about 8 batched transactions.
  • ofsecman.io: a missing WHERE turned a single-row UPDATE into a full-table UPDATE running repeatedly — over $5,000 in under ten seconds.
  • Cloudflare community: a first-time user billed $3,200 for want of an index, card overdrawn before they noticed.
  • The common finding across all three: no hard write cap, no write rate limit, and no billing alert granular enough to catch a runaway writer. The circuit breaker has to be ours. This is a standing risk for any endpoint that writes inside a retry or a cron.

Snapshot versus append-only, priced against this meter

An append-only design costs more writes than a snapshot when state changes often and each event is small: every action is at least one row plus its indexes, where a snapshot rewrites one row only when you choose to flush. For an autoplay grinder that is a write amplifier, not a saving. Compaction is itself a write; with reads a thousand times cheaper than writes, compacting to speed reads almost never pays here, though compacting to control storage at $0.20 per GB-month can, on a coarse cadence.

Keep append-only for what must survive a rollback — grants, wallet, entitlements, drops — written immediately, idempotency-keyed, minimally indexed, with a compound primary key under WITHOUT ROWID so the dedup key costs one write rather than two. The Durable Object is already the single-writer boundary, so no distributed lock is needed for exactly-once processing; exactly-once delivery remains impossible and the idempotency key is what covers the retry.

What other games do about the same problem

  • James Gwertzman (PopCap/EA), HPTS 2013. Save payload cut from 30K to 3.5K, and analytics split onto its own pipeline rather than the transactional store — because once free-to-play instrumentation landed, analytics accounted for more than half of all transactions. That is this problem exactly, a decade earlier: co-located, observability is billed at authoritative-write prices. (Retrievable as a slide deck; treat the specific numbers as from that deck rather than a reviewed paper.)
  • Nakama / Heroic Labs. Wallets are updatable only from the server, and MultiUpdate combines account updates, storage writes and deletes, and wallet updates into a single atomic transaction — the canonical shape for coalescing related authoritative writes into one commit.
  • Discord's Cassandra to ScyllaDB migration is widely cited on write-heavy game persistence, but in an LSM store reads cost more than writes — the inverse of this pricing. Its lessons do not port directly and should not be quoted as if they do.

Ranked levers

  • 1. Zero writes on read and poll endpoints. /api/grants/pending writes nine rows, six of them an automatic bug report. A polling endpoint should write nothing. Highest leverage because autoplay polls.
  • 2. Dirty-flag coalescing in object memory, flushed on cadence or session end — the mechanism that actually removes redundant writes. Authoritative writes still go through immediately; in-memory state does not survive hibernation.
  • 3. Narrow UPDATE of non-indexed columns in place of whole-row rewrites and INSERT OR REPLACE.
  • 4. Observational logs off the billed store — sampled to Analytics Engine or flushed to R2, leaving only the authoritative grant ledger in SQLite.
  • 5. Schema pass, and it is free: WITHOUT ROWID on TEXT and compound primary keys, compound indexes in place of several single-column ones, inline UNIQUE reconsidered. The kv table, at 18 write statements, is first.
  • 6. Counters to Analytics Engine rather than the usage table.
  • 7. Retention pruning on a coarse cadence. Each DELETE is a write, so prune in batches, never per request.
  • 8. Circuit breaker and anomaly detection. Not a saving — a cap on the downside the three incidents above describe.

Not yet measured on this build: which of these levers is worth what. The ranking is by mechanism, not by measurement, and it rests on the unverified assumption that whole-row rewrites and per-poll writes dominate the 10.3 rows written per request. The instrumentation in entry 6 is what settles it, and nothing should be promised as a saving before it runs.

The cause is our own migration, and it is in its most expensive state

The save-split dual write landed 2026-08-03 and widened on 2026-08-04 when all six writers of saves were routed through writeSave(). Every save now also writes save_parts and save_parts_mark. It is an argument that the half-finished state is the worst one to sit in, and it has been sat in for three days.

Schema audit (tools/schema_audit.py, step 4)

45 tables, 78 write statements. 40 of the 45 carry a primary key that creates a hidden index that WITHOUT ROWID would remove — every INSERT against them bills 2 rows where it could bill 1. No table in the build has two or more single-column indexes, so that lever is already clean. kv is the worst single target at 12 INSERT OR REPLACE sites: that shape bills 1 for the row but rewrites every index, where a narrow UPDATE of a non-indexed column rewrites none.

The one-time rebuild cost, which is what step 5 is gated on: WITHOUT ROWID cannot be added in place — it is create-new, INSERT SELECT, drop, rename, writing every existing row once per table per object. Measured across the whole roster today: items 1,833, item_grants 5,142, anomalies 4,034+ (a floor — the read door caps at 500 per account), save_hist 280 (capped at 20 versions per realm). Everything else is single digits per account. Total on the order of 11,000 rows, about one US cent. Retention is what keeps this small: drops_granted and anomalies prune at 30 days, events_seen at 7, save_hist at 20 versions. The rebuild is cheap now and scales with the roster, so the argument for doing it at fourteen accounts rather than at a hundred thousand is the whole argument.

The finding that matters

The save path is the bill. Not battles, not the leaderboard, not the WorldDO. Two of the three levers that follow are already identified and neither needs new research: halve the number of saves (the client sent two per battle until 2026-08-06), and stop each save costing double (finish the split cutover, and put WITHOUT ROWID on the 40 tables). The third — per-system attribution inside a request — still needs the WRCOST tags from step 1 to be on release, because the historical billing data has no route dimension and never will.
