UPGRADING

No pity. No failstacks. No protection. Every attempt is a pure roll. Failure costs currency only — items are never destroyed or downgraded.

Grading up (Worn → Void)

One shared ladder for gear (paid in Scrap) and enhancements (paid in Dust / Essence / Ink). Same success rates, different currencies. Soul grading (Worn → Void)

Class souls only — grading applies to souls slotted into the character's eight gear slots; creature-side souls do not grade. A class soul's grade is independent of the source creature's quality grade and is retained through the source line's advancement. All souls start Worn. SoulMult = 1 + (1/9) × (grade# − 1) multiplies the soul’s output (passive magnitude / granted move power) — Worn ×1.00 → Void ×2.00, nine equal steps, rebased 2026-08-05 from ×0.05/step which topped out at ×1.45. Which grade that reads depends on the kind of soul. A CLASS soul (CLS-*) uses its own graded field, upgraded through the ladder below. A CREATURE soul has no such field and never did — it reads the source creature’s quality grade, inherited from the egg. Creatures are not upgraded with resources; they are bred and hatched, so that lever is raised by breeding for a better egg, never bought. Until 2026-08-05 creature souls read the class field, which is unset on them, so every creature soul computed as Worn however good the creature was. LIVE on release since 2026-08-05 (0.32). See Equipment for the combined stage×grade surface. Each attempt costs mult × 5 units, payable in any combination of the four sink currencies at their income-rate weights: 1 unit = 15 Scrap = 2 Dust = 2 Essence = 2 Ink (old Ichor folded into Scrap at 15:1; each ≈ equal farm time). Same success ladder as gear. Ichor excluded — the renamed Food is battle-earned and belongs to the breeding-and-hatching economy, not the sinks.

Grading costs scale with tier (2026-07-31)

Ruling reversal, from a playtest report: the 07-29 tier-flat call let endgame income trivialize low-rung grading and undercut the tier-scaled sinks. Attempt cost now carries a Tier column in codex/grading.csv (360 rows), anchored so the T10 column is the approved hour-priced ladder unchanged and every lower tier pays the same time per rung on the measured income curve. The forge's grade surcharge derives from the same ladder at the recipe's tier, so forging can never become the cheap route at any tier — the invariant holds by construction.

Upgrading equipped gear in place (2026-07-30)

Equipped gear never appears in the bag, so the upgrade panel could not reach it. Clicking an equipment slot now offers ATTEMPT UPGRADE on the currently equipped piece: the same grade ladder, costs and success rolls as a bag attempt, resolved in place. Sockets and the scroll follow the item through the promotion (the socket identity key carries the grade, and the promotion migrates it) — this also fixed a pre-existing bug where a bag item's sockets and scroll were silently orphaned by a successful grade upgrade.

Auto-optimize (2026-07-30)

The target decides, and Overall Power breaks the tie. Optimize For maximises the chosen metric, but on a slot where that metric cannot tell the candidates apart it falls back to overall power instead of leaving the slot alone.

  • Why it was needed. The scorer returned one metric for the whole loadout. With ATK selected, the attack metric sums attack only — so on a Head or a Chest every candidate scored the same number. The incumbent is evaluated first and the comparison is a strict improvement, so the incumbent always won and those slots were never optimised at all. Not a preference gone wrong: whole slots were skipped. Report #50.
  • There is no list of which slots carry attack, deliberately. “Attack isn't available for that slot” is exactly “the target metric cannot tell these candidates apart”, which the scores already say. A class that gains an attack-bearing armour slot tomorrow is handled with no edit; a hand-written list would be wrong the first time that happened.
  • Ties still keep the incumbent. Both terms must be beaten strictly, so a loadout that is already best changes nothing.

Client: optScore2() and the candidate loop in optBuildPlan(). Probe: tools/probe_optfallback.py — BEFORE 6/6 (asserting the defence slots are skipped under ATK), AFTER 7/7.

The equipment header carries AUTO-OPTIMIZE: it proposes the strongest legal loadout from what the player owns — gear slots and tags, plus a global re-assignment of gems and runes drawn from the bag and from everything currently socketed on equipped pieces. The displayed POWER number is the single metric; slots that could host several stats resolve to whichever combination of piece and stones scores highest. Hard rules: stat-match (a stone only enters a host of its own base stat), class-locked weapons are never proposed, creatures, souls and scrolls are never touched, stones on unequipped inventory gear are not cannibalized, and ties keep the current piece so a second run proposes nothing. Nothing changes without the preview's confirmation; the preview states the exact inventory delta and is blocked by the inventory guard if the bag cannot absorb it.

Where the roll happens

The server rolls the attempt, not the client. An upgrade is chance-based, so it is cheatable anywhere else. POST /api/roll with kind:'grade' (or 'soul_grade'), the item's category, its from and to grade, its tier, and an idem key of the client's choosing. The server matches the authored row in grading.csv, draws against its Success_Pct with a secret-keyed HMAC, records the result, and answers {success, pct, cost, on_failure}. The client displays that answer; it does not decide it.

Re-sending the same idem replays the same outcome instead of rolling again, so a dropped connection or an impatient second tap can never re-roll an attempt or charge for it twice. A step that is not in the CSV is refused outright, so the ladder cannot be shortened from the client. Currency is still spent client-side and validated by the save door until inventory moves server-side.

The refresh reroll, and why the idem key did not stop it (reports #119 + #125)

Status: on release. Two players found this independently and one used it to put his entire loadout on Primordial. Fail a grade, press F5 before the game next saves, and the materials are back and the next click is a brand new chance — in the first reporter's words, “posso fazer isso ate os upgrades darem certo”. It worked on equipment and on class souls.

The paragraph above contains the bug, in the phrase “of the client's choosing”. Every property this door promised was true of a retry and none of them was true of a second attempt:

  • the draw is HMAC(SPAWN_SECRET, roll|sid|realm|kind|idem) and cannot be predicted — but idem is minted fresh by rollIdem() on every click, so a second attempt is a different key and therefore a different draw;
  • the materials are debited in the browser and only reach the server on the next save, so a reload puts them back;
  • and upgResolve() called saveRun() on every SUCCESS branch and not on the failure branch — so a failed attempt sat unsaved until some unrelated autosave. That asymmetry is why the exploit was reliable, and it is exactly what both reporters describe: “sometimes it consumes the reagents, but most of the time I can try again”. Whether the spend stuck depended entirely on whether an autosave happened to land in the window.

The fix is the pattern this file already documents twice. The creature sex roll is keyed on the creature and the egg roll on the pen and its egg number, both with the note that a fresh key is right only for “an attempt that has cost nothing yet”. A grade attempt costs something the moment the server answers, so it now belongs to the same family:

  1. the draw is keyed on the target item plus an attempt ordinal the server holds, not on anything the client mints. The client sends only which item it means (upgTargetId(), which names the instance — two copies of one item are two separate attempts);
  2. the ordinal advances only once a save has landed since the answer. Until then the same attempt is replayed, with unsettled:true. A refresh therefore returns the same failure instead of buying a new chance;
  3. the attempt is recorded by the server at the moment it answers, so it exists even if the browser never saves — which is precisely what #125's reporter asked for in his own words (“save the character right after the upgrade result”);
  4. and the client now flushes on failure as well as on success, so an honest second attempt always has a settled save behind it.

What counts as the spend landing is the save version moving past the one current when the roll was answered. The bundle is debited in the same tick the outcome is applied, so any save written after the answer carries it; the version is the cheapest honest evidence available and costs no extra write. The existing idempotence is untouched — a genuine reconnect resending the same key still gets the same answer and is still never charged twice.

Additive on purpose. A client that sends no item id falls through to the old client-keyed behaviour, because one backend serves both branches and release must keep working. The hole closes for an account the moment its client sends the field, which is at the 0.48 release. D RULED 2026-08-12: the items and board standing already obtained this way are LEFT ALONE. Fixing the door does not un-grade them and they are not being rolled back.

Client: upgTargetId(), upgAsk(), upgResolve() in play/app.js. Worker: the /api/roll handler and the roll_att table in src/worker.js. Probe: tools/probe_rollreplay.mjs 15/15, and 11/15 against the build the exploit is live on — it drives the real worker and reproduces the reported behaviour (seven attempts, seven different draws, one payment) before fixing it.

DAY-ONE DEFECT OF THIS CHANGE (report #130, 2026-08-13, fixed the same morning). The attempt table above is created only on the grade path, but the retention cleanup at the end of the roll door runs for every roll kind. So on a player object that had never served a grade since 0.48, the first scroll enchant, starter gender, bred-egg or breeding-economics roll recorded its draw and then crashed one line later — the client read the 500 as a network failure ("could not reach the server, the scroll is untouched") and re-asked under a fresh key, so the recorded draw was never collected. Nothing was consumed and nothing corrupted; new accounts could not roll starter genders at all. The table is now created unconditionally beside the roll-record table. Gate: tools/probe_rollfresh.mjs 8/8 (watched fail 4/8 on the unfixed build); tools/probe_rollreplay.mjs re-run 15/15, so the refresh-reroll door itself is unchanged.

SECOND DAY-ONE DEFECT (report #135, 2026-08-13, fixed the same day): the client sold replayed attempts as fresh ones. The server replays an attempt until a save lands after its answer — but the client's post-attempt save was a 10-second debounce, and the client treated any answer with a boolean outcome as a new draw: it debited the bundle again and applied its current step's result. A standing failure therefore read as collapsed odds and eaten Scrap (observed ~4–5% per click against an authored 20%), and a standing success was a free-promotion ladder — measured on the real client: three clicks, one authored 100% draw, an item climbing two grades free. The rule now: an unsettled replay decides nothing and costs nothing — the bench shows “SETTLING THE LAST ATTEMPT — NOTHING WAS SPENT”, holds 1.5 s, and forces the flush immediately; and every settled outcome (win or loss) now forces its flush too, so the replay window closes at network speed instead of staying open for ten seconds. Gate: tools/probe_upgreplay.py 10/10 — the real client against the real worker, with the replay condition forced by blocking the settle save.

The same door on scrolls — enchant joins the attempt ordinal (2026-08-14)

Status: On release. Everything above described the rule as if it covered grading. It did not cover enchant, and a scroll is worth more than a grade attempt: it overwrites a socket permanently and can never be removed, only replaced. The scroll door was still keyed on the client's own idem, minted fresh per click, so a bad enchant, a reload before the flush, and the scroll was back with a different draw — reroll until the enchant is the one you want.

The client half was worse here than grading's ever was. #125 fixed an asymmetry: grading flushed on success but not on failure, so whether the spend stuck depended on an autosave landing. The enchant path flushed on neither outcome. There was no race to win — the reroll window was the full ten-second debounce, every single time.

What the attempt is keyed on, and why it is not host. The obvious candidate was already on the request: host, added for #96 so the server could resolve the enchant's stat from the worn item rather than trust the client's claim. It is unusable as an attempt key, because it is the item's name — an identity, not an instance. Two slots wearing the same base piece, or the same piece on both creatures, would share one attempt, and enchanting one and then the other before a save would replay the first one's draw onto the second. The client sends the socket instead, in the shape upgTargetId() has always used for a socketed target, plus the scroll's own tier and grade:

  • the socket — sock:<sockKey>|<ki>-<j>, stable across a reload and naming one physical slot;
  • the scroll kind — because the roll's magnitude is a function of tier and grade. The overwrite dialog asks the server before the player confirms, so a cancel leaves an answered attempt with nothing spent behind it. Without this half, re-picking a different scroll on that socket would be handed the cancelled scroll's enchant and its magnitudes. Re-picking the same scroll still replays, which is the anti-reroll rule working: nothing was spent, so nothing new is owed.

The client now settles what it commits. Applying a scroll forces a save immediately — on the empty-socket path at the end of the apply, and on the overwrite path when the confirmation is accepted, which is the moment the scroll is actually consumed. Cancelling deliberately does not flush. And an unsettled:true answer now decides nothing and costs nothing on this door exactly as it does on grading: the bench reads “SETTLING THE LAST ATTEMPT — THE SCROLL IS UNTOUCHED”, holds 1.5 s and forces the flush. Without that, adding enchant to the set would have made things worse than leaving it out — the client would have consumed a second scroll to apply a draw that had already been taken, which is #135 on a new door.

egg and sex were deliberately NOT added. Both already derive from stable server-side identities — the egg from its pen and egg number, the gender from the creature key, which ignores the draw key altogether — so a fresh key cannot buy either a new draw. Adding them would regress a door that is already shut.

Client: askEnchant() and the socket picker's onPick / onSockConfirmYes in play/app.js. Worker: RK_TARGETED in the /api/roll handler, src/worker.js — a membership and key-derivation change only; the ordinal machinery itself is untouched. Probes: tools/probe_rollreplay.mjs extended with the scroll cases (live worker), and tools/probe_rollattkey.mjs 12/12, 8/12 against the build the hole is live on — a lift-based twin that runs anywhere node does, so the before/after is reproducible without a sandbox.

What the upgrade panel paints, and in which grade

A successful upgrade replaces the panel's item with the upgraded item, so gradeStep() immediately describes the next attempt — Rare → Epic. Anything painted from st.toColor after that moment is showing the colour of a grade the item has not reached. Measured before the fix: a Rare item drew rgb(163,53,238), which is Epic, and the word RARE was printed in the same purple.

  • The item is drawn in the grade it IS. The border reads the item's own grade, not the target of the next attempt.
  • The success message carries the colour it was written with. It is stamped onto upgMsg at the moment of the win rather than re-derived on every render, which is what made it drift a tier.
  • The from → to row is unchanged and still correct. It genuinely describes the next attempt, so Rare in blue and Epic in purple is what it should say.

The circle

The alchemical circle is always behind the item, not only after a success — it is the room the work happens in, not a reward for it. It is drawn as a CSS mask rather than an image so it can be tinted by the item's current grade, which means it turns blue the instant a Rare exists. A success adds a short aura ring in the grade just reached.

The aura alternates between two identical keyframes, and that is deliberate. A CSS animation only replays when its element mounts or its animation name changes, and the success gate stays true from one upgrade to the next — so a second upgrade in the same session would have played no burst at all. Alternating the name on each success is the whole mechanism.

Client: upgradeAttempt(), the upg render values in play/app.js; the panel in play/markup.html. Probe: tools/probe_upgcolor.py — BEFORE 4/4 (asserting the border shows the next grade's colour and no circle exists), AFTER 9/9.

A paid attempt is a ticket, and a ticket always settles

LIVE on release since 2026-08-08 (0.42). Reports #58 and #60: the forge takes the materials and then spins forever, showing no result. Only a relog cleared it, and the materials were gone.

The mechanism. upgradeAttempt() debits the bundle synchronously, then holds the roll back for 620 ms so the attempt animation can run. That delay used to be an entry in this._timers — the component’s general cancellable pool. clearTimers() empties that pool, and every battle path calls it: entering a fight, forfeiting, resuming, starting or ending a PvP game, entering or leaving a replay. So a battle event landing inside the 620 ms window destroyed the resolution outright: the wallet was already spent, upgBusy stayed true, and no result was ever produced. Both reporters sent with a battle resolving, which is exactly why it felt random — it needed autoplay running while the player used the forge.

The rule now. A paid attempt is a ticket (_upgPend), and a ticket always settles:

  • Its timer is _upgT, deliberately outside _timers. clearTimers() cancels animation and autoplay work; it must never be able to cancel something the player has already been charged for. The exclusion is commented at clearTimers() itself so it is not tidied back in.
  • upgResolve(id) is idempotent by ticket id. A sweep and a late timer cannot both pay out, and a repeat cannot double-charge.
  • upgSweep() settles any ticket older than 4 s whose timer was lost by any means we did not predict. It runs from both componentDidUpdate and the rAF ticker — componentDidUpdate alone would leave a ticket hanging on a screen that is not re-rendering.
  • Opening or closing the forge settles; it never cancels. closeUpgrade() previously cleared upgBusy whether or not the attempt had resolved, which is what made the broken build look like it recovered when it had simply eaten the materials.
  • The re-entry guard is _upgPend, not upgBusy alone. upgBusy lives in state and a setState that has not committed guards nothing: three clicks in one tick were measured charging 14 against a 10-Scrap bundle on the old build.

One RNG seam. The roll is now the whole of upgRoll(st) and nothing else in the forge reads the RNG. That is deliberate: item and class-soul grading is item 1 of D’s 2026-08-08 server-side-rolls order, and moving it means moving one method rather than unpicking a resolution path.

Probe. tools/probe_upghang.py, seeded on reporter #60’s own save — BEFORE 5/12, AFTER 12/12 across three consecutive runs. tools/repro_upghang.py remains the record of the diagnosis. Three of the gate’s own assertions were wrong first and were fixed rather than relaxed, and each failure mode is worth knowing: a same-tick wallet read reported the pre-charge figure, so the broken build passed the double-charge test; a fixed five-currency sum undercounted a bundle that spends outside the list, reporting “bundle 10, charged 3” on a build behaving correctly; and reading the item’s grade to prove a close had settled made the result depend on the roll — it passed on a win and failed on a loss, on the same build. The last is now spied off advEvent('UPGRADE'), which is written on both branches of the roll.

  • 2026-08-06 — the advancement trigger now reaches party creatures, and class souls join the system. LIVE on release since 2026-08-08 (0.42). What was broken. advReady() has always built its map from both advancingSoul() (keys gear slots 4–7) and advancingAlly() (keys slots 8 and 9, the creature slots). The only tile reading that map was invSlots, which is EQUIP.slice(0,8). Slots 8 and 9 render from a different list, invMons, which carried no arrow at all — so every party advancement was computed, counted in the readiness badge, and then discarded at the moment of drawing. The player was told an advancement was ready and shown no way to start it.
    Why it survived review: the comment sitting directly above advArrow claimed the arrow sits on “the teammate in equip group 8 or 9”. Reading the code agreed with the design; only the screen disagreed. A comment that describes intent the code contradicts is worse than no comment.
    Class souls. advancingClass() already existed and was already counted, so the same dead-end applied to it. It is deliberately not folded into advReady(): that map is keyed by gear slot index and a class soul has no gear slot, so a synthetic index would hang its arrow on another creature's tile. It gets its own binding on the class row, through the same playAdvance path, with the same wording and the same glyph — one advancement system, three sources.
    Where the arrow sits. On the soul tile it hangs above the tile edge. The party creature card sets overflow:hidden, so the same offset there would be clipped — present, styled and invisible. It is inset instead.
