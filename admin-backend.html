BACKEND, SAVE & ANTI-CHEAT

Hub › Dev Tools › Backend, Save & Anti-Cheat

Canonical spec (v2, July 2026) for persistence, the server-authoritative economy, Steam integration, anti-cheat, and live-service cost. Supersedes the v1 draft. Stack per GDD: UGS (Auth, Cloud Save, Cloud Code, Leaderboards, Remote Config) + Steamworks.NET + Steam Inventory Service. One sentence: the client sends events and requests, never state; the server owns state and computes every result; Steam Cloud carries preferences only.

The principle & trust boundary

Local editing is not prevented — it is made inert. "I have 999,999 Scrap" is state and is never an input to any write. "Craft recipe R" / "I completed battle #8837" is a request or event, validated against the server's own copy of the data. The client keeps a disposable prediction cache for responsiveness; every Cloud Code return overwrites it with the authoritative snapshot. There is nothing to clean up after a cheat attempt because the illegal state never existed server-side.

Fig. 1 — Trust boundary and storage topology. Everything that gates loot, rank, trade, or death lives right of the boundary.

Data classification

Every persisted category maps to one authority, one store, one access class, one flush policy. Rule of thumb: if faking it affects loot, rank, trade, or death → Protected/Private on UGS, server-written. If faking it only affects the player's own convenience → client-local.

Access classes are the structural wall — a Protected/Private key physically cannot be written by the client SDK. Validation logic is the second layer. Keys are namespaced per realm (eternal.* / hardcore.* / seasonal.* / hcSeasonal.*); Codex and playerLevel are account-wide. State is written as consolidated documents per realm, not per-field keys — every extra key per flush is another billed write.

The economy transaction contract

Every spend — craft, refine, grade-up, soul grade, breed, enhancement — is the same atomic transaction computed against the server balance. Ordering is the entire guarantee: check, then atomically debit + grant, else reject whole. RNG rolls (refinement 100→1%, grading 100→0.5% ladders) resolve server-side, so a failed roll cannot be re-rolled by save-scumming — the currency is already gone on the server. Costs come from the same authored tables as the GDD (25×tier Scrap crafts, 3×lvl×tier refines, the 1/1/2/3/5/8/12/18/40 Ichor ladder, the five-material soul bundle).

Fig. 2 — Transaction gate. The "player edits Scrap and crafts ten items" scenario dies at the first read: server sees 40, all ten requests reject, zero items ever exist.

Rewards, batching & flush tiers

Rewards are derived server-side from completed battles; the client cannot assert an amount. Per event, Cloud Code recomputes Food (round(2×(1+lvl/20)×RarityMult)), XP with the level-penalty curve, and rolls the 10%/10% gear/enhancement drops from server tables — then applies one aggregated write. Batching groups events at the Cloud Code boundary: it changes how often we write, never who decides what is written.

Fig. 3 — Reward path. Immediate-tier events can never sit in an unflushed buffer; batched-tier loss on crash is bounded to a few minutes of personal grind — an availability tradeoff, never an economy hole. Replay reuses the GDD's determinism primitive (initial state + seed + committed move log).

Rate cap — variable battle speed

Battle duration is not constant: a floor-1 one-shot is far faster than a 5-turn endgame fight (the economy sheet's 280 Food/h at floor 1 already implies ~85+ battles/h there vs ~30/h endgame). So the cap is a curve derived from each battle's committed turn count, not a flat battles-per-hour number. Elapsed time is measured between Cloud Code's own flush timestamps — client clocks are never trusted.

Fig. 4 — Turn-count time floors. Guarantee: no account accrues faucet output faster than the design pacing curve for the content it fights. A headless client can forge 1,000 logs in 10 s of CPU — they credit at design pace, so the farmer gains exactly nothing over legal autoplay. Forged 1-turn logs against enemies the server-known party can't one-shot fail the sampled replay.

Log integrity — hash chain

Each battle event carries the previous event's hash. The server stores only the chain head per session; full logs stay client-side and are requested on audit. Streak and floor-record history becomes tamper-evident at ~zero storage cost.

Fig. 5 — Hash-chained event log. Editing, inserting, or deleting any past battle breaks every subsequent hash.

Concurrency — the actual historical dupe vector

Server-authoritative games get robbed through their transaction layer, not the client. The classic dupe: two simultaneous spend requests both read balance 100, both pass validation, both commit. Two mechanisms close it, both mandatory before trading exists: every request carries an idempotency key (retries return the cached original result), and every Cloud Save write uses the writeLock version token so concurrent writes to the same player document conflict and retry serially.

Fig. 6 — Optimistic concurrency + idempotency. 100 gold cannot become 200 gold of spending regardless of request timing.

PvP — commit-reveal, verify once

Rounds run peer-to-peer over Relay; the server is not in the per-round loop. Each side commits hash(move‖nonce), then reveals; the round's RNG seed derives from both nonces, so neither side can peek at the opponent's pick or steer a roll. Committed rounds persist before resolution renders (the GDD's anti-scum rule). At match end, one Cloud Code call replays the committed log, verifies it against both players' commitments, and writes the ladder — server-only. Timeouts and disconnects follow the PvP page: autoplay AI picks on expiry, five consecutive AI rounds forfeits.

Fig. 7 — Commit-reveal PvP with single end-of-match verification.

Hardcore death — one atomic commit

Death is confirmed server-side (the losing battle is replay-verifiable), then the whole pipeline applies as a single transaction. The death mark lives in a Private key the client cannot read, let alone clear; it is written atomically with the Bequest seal, so a wipe without a seal — or a seal without a mark — is structurally impossible. Sealing also transfer-locks the Steam-owned assets into the receiving crypt so nothing can be duped out mid-death. The HC-Seasonal → Hardcore double-migration (the GDD's highest-risk path) is a scheduled, idempotent server job at season end — never client-driven.

Fig. 8 — Hardcore death pipeline. Test all four realm paths and the season migration independently, per GDD critical risks.

Steam market & farm accounts

The mint is downstream of validation: a Cloud Code transaction confirms the asset was legitimately earned or paid for, then calls Steam GenerateItem with the publisher key and binds the instance ID back to Cloud Save. A faked balance never reaches the mint — the only thing touching the real-money market is the one thing that cannot be spoofed. Every trade path goes through a server-side transfer lock with a single-ownership check (in place before the marketplace opens, per GDD critical risks), and every item class carries a config-level tradeable flag so a compromised category can be frozen without a patch.

With client edits neutralized, the residual economic threat is farm accounts — F2P + legal 24/7 autoplay + a real-money market invites item-printing at account scale. Every farm account plays "legitimately," so this is fought with gates and telemetry, not client tech:

Live-service cost model

UGS pay-as-you-go unit prices (July 2026): Cloud Code $1.50/M invocations + $0.00002 per compute-second (1M invocations + 20 compute-hours free/mo); Cloud Save $2.50/M writes, $0.90/M reads, $0.50/GiB stored (1M + 1M + 5 GiB free); egress $0.25/GiB; Relay $0.16 per average monthly CCU after the first 50; Leaderboards currently "free for a limited time".

Load model: autoplay per the GDD; flush every 20 min + ~1 immediate event/h ⇒ 4 Cloud Code invocations/h/CCU, each 1 consolidated-doc read + 1 write, ~50 ms compute, ~1 KB delta response; CCU treated as sustained 24/7 (autoplay worst case, 730 h/mo); PvP = 2% of CCU, commit-reveal, 2 verify calls/match, Relay transport; storage 50 KB per stored account.

Traffic blocks — the rate limiter's second layer

Every authenticated /api/* request is sorted into a rate class and spends a token from a per-account bucket for that class. The classes and their buckets (src/worker.js, RATE): battle 12 / 1 per min, floor 15 / 4, save 10 / 6, save_read 30 / 30, name 3 / 0.05, auth 10 / 10, db 40 / 20, wallet 12 / 20, other 20 / 12, plus a blanket ip_all of 240 / 120 per address. An empty bucket answers 429 {error:'rate'}.

wallet exists because a generic bucket punished a normal player (2026-08-04). /api/wallet/spend and /api/shop/buy matched no prefix, so they fell into other and shared its 20 tokens with hatching, breeding, feedback and the shop catalogue. A player mid-session has only a handful left, so a couple of quick clicks on the inventory + button returned 429 — shown to the player as PURCHASE FAILED with no reason, and, worse, passed to reportBreach, which files that account into the traffic table. Mashing a buy button looked like abuse in our own anticheat record.

These calls spend the player's own currency, are server-validated and carry an idempotency key, so repeating one mints nothing: the limit is there for server cost, not for economy abuse. The class is therefore sized so a legitimate player cannot reach it — the client paces purchases at one per five seconds behind a confirmation gate (12/min) while the bucket refills at 20/min with a burst of 12 for someone buying several slot tiers after topping up. Measured: mashing from a full bucket is refused on the 13th call, while thirty purchases at the client's pace never take the bucket below 11 tokens. The client is the pacer; the bucket is only the backstop. A rate class that a normal player can reach is a bug report waiting to be filed against the wrong subsystem.

A refusal also escalates. reportBreach posts the (account, class) pair to the WorldDO at most once per RATE_FLAG_MS (default 60s); once TRAFFIC_BLOCK_N reports (default 3) land inside a rolling 10 minutes, traffic_status is set blocked=1 for that pair and an anomalies row is written. A blocked pair is refused at the gate with 403 {error:'soft_block'} before any Durable Object wakes. The worker caches the block set per isolate for SB_TTL_MS (default 60s), so a change takes up to a minute to be felt.

Reads are exempt (2026-08-02). Classes listed in RATE_READ_ONLY — currently only save_read, i.e. GET /api/save — are never soft-blocked and never escalate. Reading your own save grants nothing, so blocking it prevents no abuse; and because the shell RETRIES that read when it fails, escalation on it meant the retry loop fed the counter that produced the block. Nothing may join that set which can mutate state or mint a value.

Blocks expire (2026-08-02). /api/_internal/softblocks clears blocked=1 rows older than SB_EXPIRE_MS (default 1 hour) each time the set is read. The row survives with blocked=0, so /api/admin/traffic history and the traffic audit table are unaffected, and a genuine abuser is re-blocked by the next 10-minute window. SB_EXPIRE_MS=0 restores permanent blocks. Before this, blocks were permanent and cleared only by hand — the flag detail said “queued for review” and there was no queue.

Failure mode this class of block produces, and how to recognise it. A soft block is per (account, class), so the account keeps working everywhere else. With save blocked, GET /api/me still answers 200 (class other) while GET /api/save answers 403 forever. The shell reads that as a failed sync and falls back to the sign-in gate, so the player sees “Could not load your save — retry N…” under a Steam button and reports it as “I cannot log in”. It is not a login failure and re-authenticating cannot help. Diagnose with the account's own cookie: curl -i https://playdfmc.com/api/save -H 'cookie: ht_session=…' — 403 is a block, 429 is the bucket, 500 is the object.

Dismantle yield — the shared table

src/dismantle.js is a pure module carrying the dismantle yield: dismYield, breedRates, gradeNum, buildDismantleDb, dismTotals. Same contract as src/power.js — no fetch, no timers, no Durable Object state, safe to import from the Worker and from node, with CSV fetching left to the caller Worker-side and never inside a DO.

Why it had to exist. POST /api/backup/dismantle removes rows and credits nothing, because the yield lived only in play/app.js. That makes the ops door unusable on a real player: it would delete a pile and pay for none of it. Separately, foodCeil derives its allowance from battle income only, so every Ichor a dismantle pays today is client-minted and survives purely on the grace allowance.

The yield is AUTHORED, not computed. dismantle.csv carries one row per (Category, Grade, Tier, Refinement) and the module only looks it up. The ladders are deliberately not smooth; there is no formula to derive and none should be written.

Gear|<Grade>|+<Refine>|<Tier 1-10>Weapon, Armour, Accessory — blank Tier defaults to 1
<Cat>|<Grade>|<Tier>Gem, Rune, Scroll, Tag — Tier carried verbatim, not defaulted
Key|Worn|<round(floor/10)>Boss keys, on the tier ladder
Material|Worn|<Tier>Materials
— (no table lookup)Egg and Monster: breeding.csv Egg_Dismantle_Ichor at the item's grade. A creature salvages for the same Ichor as an egg of its grade (D ruling 2026-07-24).

null is not zero. Class souls, anything flagged dismantleable:false, an unknown category and a missing CSV row all return null. A caller that reads null as zero would silently confirm a zero-yield dismantle, which is how a player loses a pile for nothing.

The parity gate. A transcription is worthless unless something proves it has not drifted, so tools/probe_dismantle_parity.py boots the real client and compares against it: the rebuilt table key-for-key and value-for-value, then dismYield on a fixture generated from every authored row plus every creature grade plus the null cases, then the aggregate. Fixtures come from the CSV, so a newly authored row is covered the day it lands. Currently 9/9 over 1,540 fixtures from 1,515 rows.

Not yet enforcing. The module exists and is proven; nothing validates against it yet. The design (D): the player dismantles, the client credits immediately — safe, because a dismantle carries no RNG — the save rides the next sync, and the server recomputes and validates by diffing the previous save against the new one. Items gone from the bag are what was dismantled. A client receipt is never trusted, because a receipt is precisely what an attacker writes.

Server: src/dismantle.js. Gate: tools/probe_dismantle_parity.py. Client source of truth transcribed from play/app.js dismYield/breedRates/gradeNum/dismantleDb.

Ops reads — the account's own record

Both are key-gated with the ops key and are read-only: they select, they never write. They exist because /api/admin/* is dispatched to the WorldDO while saves, anomalies and progress live in the player's own object, so the admin console's save-history and flags views have always answered empty for player data. That routing defect is still open; these doors are what made the 2026-07-31 rollback repair possible.

DoorAnswers
GET /api/backup/history?key=&sid=&realm=The version ring for that account — ver, ts and size for the last 20 saves; add full=1 for the payloads. Gaps in it are diagnostic: a player who is clearly playing while no version lands is a client that has stopped uploading.
GET /api/backup/facts?key=&sid=The server's own record for the account: the progress ratchet per realm and the ledger it built from credited battles (xp, food, kills, battles). This is the honest basis for any repair — it is what the server credited, not what a client claimed.
Repair discipline. Restore only what the server can prove. The ratchet proves floors; the ledger's xp proves character xp because xp is earned and never spent. It does not prove currency: food_total is cumulative earned, and a player has spent some of it, so restoring a wallet from the ledger mints money. Never send a placeholder payload to a live account to test the door — /api/backup/restore sets the ratchet from data.maxFloor, so a stub body resets the account's climb to 1.

Restore is not a save. /api/backup/restore writes the saves row and the progress ratchet and nothing else — it does not add a save_hist version and it does not write save_parts, because writeSaveParts() is called from the save door alone. Two consequences. First, a restored version is invisible to GET /api/backup/history: the ring can top out one version below what export&live=1 returns, and that gap is the restore, not a lost write. Second, once the save split cuts reads over to parts, a restore would install a save that no part reflects and the player would load the stale parts instead — silently discarding the repair. Every writer of saves must write the parts before that cutover.

2026-08-04 — the detected-but-unenforced flag class reports itself (ON DEV). Fifteen flag kinds now file a bug report into the same inbox as player reports, with kind='auto' and status='open', instead of waiting in the flags door to be found by hand. Written server-side on purpose. The obvious route was the client's automatic report, and that was rejected: sending a server detection back through the client tells the client which guard fired, which is the exact criticism of headOk — computed, flagged, returned to the caller, gating nothing, so the reply announces the catch. The client is told nothing.

It is an allowlist, not everything. Most flags are routine and reporting them would bury the ones that are not. Reported: dismantle_claim_bad, inv_unsourced, party_line_dupe, grow_only_map, maxfloor_regress, wraithgold_over_grant, save_conflict, stale_instance, chain_break, xp_over_ledger, classxp_over_ledger, ichor_over_ledger, boss_floor_anomaly, floor_oob, roll_rate. Deliberately excluded, each for a reason: grow_only (the normal outcome of a grow-only merge, 237 on one account), save_oversize and save_large (the save ceiling, owned by the split), rate_cap (the cap doing its job), and dead_slot (measured benign — a legitimately resumed battle claims a spawn the server already marked dead, so reporting it would report honest players).

Deduped and budgeted. One report per account per kind per day, held on disk rather than in the isolate's memory, because an isolate restart would otherwise file the same report again. Forty automatic rows a day across the whole inbox, because the failure mode of a reporter is a systemic bug filing thousands of rows and burying every real report including its own. The flag row itself is written regardless: the reporter has its own try and can never stop the evidence being recorded.

None of this enforces anything. These guards still gate nothing; what changed is that they now arrive somewhere they will be read.

It now returns fresh, saves_ver, mark_ver, gen and mark_gen beside n and rejoin_ok. fresh is the stage-3 gate in miniature: the parts are only servable while the stored watermark equals saves.ver and the wipe generation matches. Watch it before the read cutover — once every writer goes through writeSave() a not-fresh account should be rare, and a sustained rate names a writer still bypassing the facade.
GET /api/backup/pvpq?key=The PvP queue: one row per node with age_ms, and a count of how many are pairable right now. Age is the point — the pairing window is 12 s, so a live node and an expired one are indistinguishable until you subtract. Fewer than two pairable nodes means nobody can be matched, and the door says so.
GET /api/backup/export?key=&sid=&realm=&live=1The save. live=1 matters. Without it the read comes from the R2 mirror, which is a nightly copy — a player who started today has no R2 object at all, and reading that absence as “no save” is wrong. The authoritative save is always in the player's own Durable Object, with 20 versions of history, from the first write. R2 is off-site disaster recovery, not the store.
Route placement is load-bearing — this is a real defect class, not a style note. MainDO.fetch carries a blanket session gate partway down its body: if (!ses) return json({error:'unauthenticated'}, 401). Every route defined below that line requires a player session. The Worker calls an internal route with x-internal: 1 and no session cookie, so any /api/_internal/* handler written below the gate is unreachable: ses is null, the object 401s, and the Worker forwards that status verbatim. The ops door then fails with unauthenticated even though the caller's ops key was correct and the door beside it answered.

Invariant: every /api/_internal/* handler lives above the blanket gate. The symptom is diagnostic — an ops door returning 401 unauthenticated rather than 403 forbidden is a placement failure, because a bad key produces 403 at the Worker and never reaches the object at all.
