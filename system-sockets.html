SOCKET OWNERSHIP

Other Systems › Socket Ownership

What happens to a gem, a rune or an enchant scroll when the item holding it leaves an equipped slot. Three code paths take a piece out of a slot and all three must obey one contract. Until 0.45 one of them did not, and it destroyed 41 stones for a live player in a single click. Companion page: Equipment & Auto-Optimize.

The contract

RuleMeaning
Gems and runes are refunded LOOSEThey come back to the bag as their own items, one row each, marked unsocketed. They do not travel with the piece.
An enchant scroll is NOT refundedIt rides with the item, folded onto that item's own bag record as .socks. A scroll is bound to the piece it was applied to and unfolds when the piece is equipped again.
The socket entries are deletedEvery key under that item's prefix is removed from sockOv. A stone is never left addressed to a slot that no longer holds its item.
Bag room is checked FIRSTinvRoomFor() is asked before anything moves, counting the item plus every gem and rune coming back. The check is 1 + gemRuneCountAt(gi) per occupied slot — scrolls are excluded on purpose, because they need no room of their own.
A refusal is reported upwardThe path returns false rather than half-completing, so a caller cannot announce a change that did not happen.

Gems are socket kind 0, runes 1, scrolls 2 and above. Every refund branch in the code is written as ki < 2 versus ki >= 2, so the split is that one comparison in all three places — not three separate opinions about which items are refundable.

The socket key, and why it is shaped this way

A socketed stone is stored in sockOv under a single flat string:

PartSourceExample
Item identityoptIdentOf() — sk|name|grade|tiersk|Exalted Signet|Rare|7
Instance@ plus the equipped slot index|@2
Socketkind and position|0-1

The @gi half exists because the identity half is not unique: two copies of the same piece at the same grade and tier produce the same identity, and before the instance suffix they shared one set of sockets — the second copy displayed the first copy's gems. claimLegacySocks() migrates any surviving flat key to its own instance, lowest slot index first, and is idempotent, so re-adopting a save claims to exactly the same keys.

The key is deterministic, and that is what makes a mistake survivable. Nothing random is stored in it. The same item, at the same grade and tier, put back into the same slot index, produces a byte-identical key.

The three paths that empty a slot

PathFunctionReached from
Manual unequip and swapequipItem()The equipment screen. The leaver refunds and folds; an arriver carrying .socks unfolds them into the new key
Auto-optimizeoptApply()OPTIMIZE. Every displaced piece takes the same route, and stones evicted from the plan return loose
Changing classswitchClass()Strips all eight character gear slots at once (gi 0–7: Main Hand, Off Hand, both Accessories, Head, Chest, Gloves, Feet). Creature Tags are not touched

A grade promotion is deliberately not on this list: an equipped piece upgraded in place keeps its stones, because optMigrateSockKeys() rewrites its keys from the old identity to the new one. The grade is part of the key, so without that migration a promotion would strand its own sockets.

⚠ What went wrong — reports #90, #91 and #92

switchClass() was a third, bare copy of the unequip logic. It pushed the naked item to the bag and did nothing else: no refund, no fold, no key deletion, no room check. Every stone in all eight slots was left addressed to a slot that no longer held its item. A player lost 41 stones in one click and filed it three times before the cause was found.

There are two doors into that function and only one of them warned. The SWITCH CLASS button on the equipment screen raises a confirmation; equipping a class soul from the soul bag (itemDetEquip → equipClassSoul → switchClass) raises none at all. That is why the repair had to live inside switchClass — patching either call site would have left the other one destroying stones.

Two more defects sat on the same lines. An emptied slot holds a truthy {name:''}, and the old read fell back to the implicit starter piece whenever the override said empty — so every switch after the first minted another copy of it, unbounded. And with no room check at all, the path could push the bag past its own cap.

Fixed in 0.45. Gates: tools/probe_classswap_sockets.py (gem, rune and scroll all lost before, PASS after), tools/probe_classswap_dupe.py (bag 2→4→6→8 over four toggles before, flat at 2 after), and tools/probe_soulbag_classequip.py against the reporter's own live save (3/6 before, 6/6 after — 41 of 41 accounted for: 32 refunded loose, 9 folded onto their items).

A stranded stone is recoverable — until the item is graded or dismantled

Because the key is deterministic, a stone orphaned against an empty slot is not lost:

Action on the stripped pieceOrphaned stones
Re-equip it — same name, same grade, same tier, same slot indexRecovered. The key regenerates identically and the stones reappear in their sockets
Grade it first, then re-equipDestroyed. The grade is part of the identity, so the new key does not match and nothing migrates an unequipped piece's orphans
Dismantle itDestroyed. The item that owned the key is gone

Anyone triaging a report of missing stones should say this before saying anything else, because the window closes the moment the player tidies their inventory. enforceSockStats() reports mismatched sockets and deliberately never writes to sockOv or the bag, so a sweep cannot close the window either.

⚠ The lesson: UI text is a claim about a code path

Both class-switch confirmations told the player the exact opposite of what the code did. The equipment screen promised that gems, runes and enchants stay socketed; the class soul's detail panel promised sockets and enchantments travelling with their items. Neither was ever true of that path, and that sentence is the reason the player felt safe clicking it — three times.

Any UI text that promises what happens to a player's items must be checked against the code path it describes, not against what the feature was meant to do. Both strings now name the real behaviour: the gear returns to the inventory, gems and runes come back loose into the bag, and each piece keeps its own enchant scroll.
