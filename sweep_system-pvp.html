PVP, TIMERS & PERSISTENCE

Other Systems › PvP, Timers & Persistence

Ranked 3v3 (avatar + 2 creatures per side), best of 3, team locked at match start, double-blind simultaneous move selection. This page defines the PvP screen, the move timers, how battles survive crashes and disconnects, removed-mode quit-out rules, and the leaderboards.

Move timers

Both sides pick all their moves for the round simultaneously; timers exist to bound the round, not each unit. The design follows the banked chess-clock model competitive simulators converged on, sized to our 10–16-turn fights.

TimerValueRule
Round timer (PvP)30 sBoth players pick within it. Resolution/animation time does not count.
Personal bank (PvP)90 sDrawn from only after the 30 s round timer is spent, chess-clock style. Never refills during a game; resets between games of the Bo3.
On expiry—The autoplay AI picks for you — the same AI that runs PvE grinding, not "first move in the list." Losing time costs quality, not the game outright.
Damage ramp (PvP)×1.5 @ 20 → ×3 @ 40+Replaces the 30-round hard cap and its tiebreak (2026-08-16). From round 20 every hit and every lingering damage tick, both sides, is multiplied: ×1.5 at 20, ×2 at 30, ×2.5 at 35, ×3 from 40 on and holding. A game ends only on a wipe — the ramp guarantees one, so no tiebreak is needed or exists. A hot ×-chip beside the round counter shows the live multiplier from round 20. PvE never ramps. Replays of Competitive games ramp identically — playback must re-produce the recorded fight.
PvENo timerMove timers are a PvP-integrity tool; against the AI there is nothing to protect and autoplay already exists for players who want speed. PvE battles instead get full crash-safe resume (below).

Persistence — battles survive anything

Every battle is a deterministic replay: initial state + per-round RNG seed + committed move log. That single decision buys crash recovery, reconnects, replays, and removed-mode integrity all at once.

RuleDetail
Save cadenceOnce per round: both sides' committed choices plus the round's RNG seed are persisted before the resolution is shown. One small write per round.
PvE crashRelaunch resumes the battle at the top of the current round — same state, same seed. Nothing is lost and nothing rerolls.
Anti-scumBecause the seed is committed before results render, killing the game after seeing a bad roll and reloading replays the identical roll. There is no outcome to reroll, ever.
PvP authorityUnity Relay is a packet relay, not a simulating server — both clients run the deterministic sim in lockstep, kept honest by the Competitive-integrity layers below. Reconnecting replays the committed log to the current round.

Disconnects

CaseRule
PvP disconnectThe match does not pause and timers keep burning — pausing on disconnect is a documented exploit vector (players firewall-drop to buy free thinking time). When your round timer + bank expire, the autoplay AI plays your side, exactly as on a timeout.
Reconnect windowReconnect at any point and control returns at the next round. After 5 consecutive fully-AI rounds, the game is forfeited — long enough to survive a router reboot, short enough that a rage-quit cannot hold the opponent hostage.
PvE crash / quitIdentical outcomes: resume at the current round on next launch. A battle in progress can be resumed but never abandoned.

removed-mode & Alt+F4

The classic removed-mode failure mode is the logout escape: kill the client the instant a fight goes wrong. Turn-based rounds close that door structurally.

RuleWhy it holds
Battles are resume-onlyAlt+F4, crash, and power loss are indistinguishable and all lead to the same place: the battle resumes at the top of the current round with the committed seed. Quitting never exits a battle.
Committed rounds standOnce both sides' moves are locked, resolution is deterministic and already persisted. If the round that kills the character has committed, the death happens on resume — watching it or not changes nothing.
No mid-round escape valueKilling the client before committing a move just returns the player to the same decision with the same information. In a turn-based game there is no "leave the server before the hit lands" — nothing advances without a committed round.

Competitive integrity

Unity Relay forwards packets between two untrusted clients — there is no simulating server in the loop. Integrity therefore comes from five layers, each cheap because battles are already deterministic replays.

LayerMechanism
1 · Team legalityNever transmit derived values. A team submission is inputs only — creature ID, level, quality, tags with every gem/rune/enchant, gear, souls, moves. The validator recomputes all stats from the committed formulas, so an impossible stat cannot be expressed. Rule checks against codex data: moves ⊆ learnset, stage consistent with level, grades 1–10, gear tier/grade/level-req legal, enhancement tier ≤ gear tier, sockets ≤ grade allowance, enchant rolls inside authored ranges, weapons class-legal, souls on armour slots only with legal granted moves. Both clients and a Cloud Code function run the identical validator.
2 · ProvenanceRules cannot prove an item was earned. The rated queue requires the team to be a subset of the account's server-known inventory — Cloud Save Protected keys ledgered by Cloud Code (UGS Economy was evaluated and rejected in the save-architecture review: 14× the per-write cost for the same guarantee) — the one strictly server-side layer.
3 · Commit–reveal roundsDouble-blind between peers requires it: each round both clients send H(move + nonce), and reveal only after both commits arrive. A reveal that fails its commit is an instant forfeit. The round's RNG seed is H(revealA ‖ revealB ‖ roundN) — derived from the reveals (nonces included), never from the commits. Seeding from commits is grindable: whoever commits second knows the opponent's commit and can brute-force nonces until the resulting seed rolls in their favour. Seeding from reveals closes it — the second committer cannot compute the seed without the opponent's still-secret nonce. Residual edge — refusing to reveal after seeing the opponent's reveal — is priced out: a player who commits but fails to reveal within the round window forfeits that round's actions entirely, and the round counts toward the 5-AI-round forfeit counter. Dodging one bad roll costs a whole silent round. One mechanism provides blindness and unriggable randomness.
4 · Per-round checksumAfter each resolution both clients exchange a truncated SHA-256 of the canonical battle state (fixed serialization order, RNG cursor included). Match → continue; mismatch → escalate to layer 5, never argue locally. Requirement: battle math is integer / fixed-point with pinned rounding points (random band as an integer 90–110 roll /100) — float math diverges across CPUs and would fabricate desyncs between honest players.
5 · Replay adjudicationEvery rated match ends with one verification call: both clients submit signed move logs, a Cloud Code function replays the battle deterministically, and only its verdict posts to the ladder. Checksums are the in-match tripwire (early abort on divergence); the replay is the authority, and at one cheap integer-math replay per match it costs a rounding error next to per-round server resolution (the save-architecture review priced that difference at ~$13k/month at 500k CCU). Checksums detect; replay decides. A cheater can desync a match but cannot win one.

Per-round input validation runs on both sides regardless: the chosen move is one of the unit's four, its cooldown is legal, the target is legal. Malformed actions die before resolution.

Matchmaking — the server owns it

ON RELEASE from build 0.36 (2026-08-06). This section replaces the peer-discovery queue entirely. A player presses FIND MATCH and the client posts a ticket to POST /api/pvp/mm/queue. From then on it polls /api/pvp/mm/poll and renders whatever status comes back. The client does not read the pool, score candidates, choose an opponent, create a match, or hold an identity. There is no decision left on the client to get wrong.

Why the old design failed, and why bounding it was not enough

The queue used to be peer discovery: every client wrote its own node with ts = its own Date.now(), read everyone else's, and judged freshness with myClock − theirClock. On 2026-08-06 a player's PC ran 3m 40s fast (measured on the ops door as age_ms -220103). His client therefore judged every legitimate match to be 220 s stale, discarded it, wiped its own pairing marker and kept queueing in silence, while his opponent sat out the 28 s team wait and was told the opponent never readied. Which of the two symptoms appeared depended on which side held the lower player id. A first fix stamped timestamps server-side and let the client measure its own drift; that worked, but it left the client correcting itself, so a missing header would silently restore the bug. The authority was in the wrong place, and that is what this rewrite moves.

Identity, rating and name are all server-owned

  • Identity is acctKey(steamid), derived from the Steam session the Worker has already signature-verified. The old random localStorage player id is deleted — a player can no longer name themselves to the matchmaker or write into another player's slot.
  • Rating is read from the player's own ladder row on the server. It used to be a number the client put in its queue node, which is a matchmaking input a player must never supply about themselves.
  • Name comes from the names table. It briefly fell back to a client-supplied string when no ladder row existed, which would have let a player queue under someone else's name; caught by running the endpoint, not by reading it.
  • One ticket per account, enforced by the primary key, so a player can never be in two matches and have to choose.

Time never crosses the boundary

Every deadline the server sends is a duration remaining (closesInMs), computed against the object's own clock. Nothing in the payload is an absolute timestamp, so there is no comparison left for a wrong clock to poison — the whole failure class is gone by construction rather than bounded. Liveness is a server-held lease, not a timestamp the client re-stamps: the ticket carries lease_ms, renewed only once it is in its second half.

Pairing

One indexed read of the pool ordered by rating, then a single sweep pairing nearest neighbours oldest-first. The band opens with the ticket's server-measured age — 25 points, widening by 25 every two seconds, capped at 5000. A match is created by inserting a row whose pair_key carries a UNIQUE constraint: the constraint is the arbiter, replacing the old “lower player id creates the match” convention, which was a rule two clients agreed on with nothing enforcing it.

The lifecycle, and why nobody can hang

phasewhat has to happenif it does not
readyboth sides press JOIN MATCH within 20 sthe match is cancelled; whoever readied goes straight back into the pool, the other is dropped
teamsboth teams posted within 30 scancelled, same rule
livethe server hands both teams down and the battle starts—

Both sides are moved by the server or neither is, so the old failure — one player waiting 28 s and being told the opponent never readied while the opponent saw nothing at all — cannot occur. Cancelling also returns the other player to the pool immediately rather than making them wait out a dead window.

Cadence and cost

The poll interval is dictated by the server (pollMs, currently 2000 ms), so load can be shed centrally without shipping a client. It has its own rate bucket (mm, cap 60, 45/min) rather than sharing db with the round exchange and the leaderboards: at a one-second poll the old shared bucket refilled at 40/min against 60/min of demand, so a player queueing for two minutes would have started answering 429 while the timer kept counting. An ordinary poll writes zero rows — the lease renewal is a single conditional UPDATE whose WHERE matches nothing until the lease is half spent. Sweep and pass are coalesced to one tick for the whole object, so a thousand players polling do not cause a thousand passes. There are no timers, no alarms and no sockets: the object stays hibernatable.

Failure is visible

A matchmaking call that fails says so on screen, and three consecutive failures stop the queue outright rather than leaving a timer counting against nothing. That silent shape — the screen saying LOOKING while the server held no ticket at all — is what made the original bug so hard to see.

Limits, measured

A pass over 1,000 queued takes ~120 ms and 5,000 takes ~320 ms, both inside the one-second tick; 20,000 takes ~1.6 s, which exceeds it, so passes would stack. Single-object matchmaking is therefore good to roughly 5,000 concurrently searching — not registered, not online, actively searching at the same moment. Above that it must shard by rating band with promotion to a shared overflow object; the design is recorded in BACKLOG.md and in research.html entry 9, and deliberately not built yet.

What is NOT server-owned yet

Matchmaking is authoritative through to the moment the battle starts. The per-round commit-reveal exchange still runs over the /api/db facade under m/<mid>/g<n>/r<n>/<side>, now authorised from the match table rather than from a client-written node. That path was audited for the same clock disease and is clean: the only timestamp it carried was written and never read, and has been removed. Moving the round protocol server-side is the anti-cheat project, not this one.

Joining out of a PvE battle — pause, never forfeit

ON DEV, not yet on release. A match can be taken in the middle of a PvE fight. Owner ruling: that fight is paused and restored afterwards — it is not forfeited and nothing is lost.

  1. On JOIN, the PvE fight is written to its own snapshot slot as stage park. Parking works from any battle phase, not only the phases that already persist.
  2. The PvP match takes the screen. The two fights cannot collide because the snapshot is split by kind (see system-networking.html); before that split, taking a match destroyed the paused fight.
  3. When the player closes the PvP result panel, the parked fight is restored — same round, same units, same floor, same seed.

The server holds nothing mid-fight: a spawn slot is marked dead only when a kill is credited, so the paused enemy is still standing when the player returns, and battle chains are keyed per chain id so a PvP fight cannot break a paused PvE chain's continuity.

removed-mode refuses the join. removed-mode already forbids leaving a battle — forfeit is refused there too — so taking a match out of a live removed-mode fight is blocked and the player is told why. Queueing itself is unaffected: a removed-mode player may queue, and may take the match from anywhere that is not a live fight.

Locking in — how a round is agreed

Neither player may see the other’s moves before choosing. A round is agreed in two phases: each side first writes a hash of its moves, and only once both hashes are present does either reveal the moves themselves. The round then resolves from a seed derived from both sides, so the same pair of inputs always produces the same round.

A commit is only real once the server has taken it. The write is awaited and retried; the player is shown as locked in only after it lands, and if the commit later goes missing from the match record it is sent again. This matters because every downstream step tests for your own commit being present — including the timeout that resolves a round when the clocks run out. Until v0.34 the client marked itself locked before writing and discarded the result, so a failed write shut three doors at once: it blocked its own retry, the opponent never saw a commit, and the timeout could not fire either. Both players waited forever.

The client may never invent an opponent. A match comes from the queue meeting a real partner or it does not happen. There is no simulated opponent, as a game feature or a testing one, and no fabricated name, rating or lock countdown.

The match HUD, and what the decree stamp means

The round/bank/game readout sits directly under the turn-order button, on the same centre axis, in one row. It was anchored bottom:648px, which on the 1080 stage puts it mid-screen across the battlefield. It is anchored to the top for the same reason the button is: a bottom anchor moves with every change to the panels below it.

The band between the button and the creature sprites is about 40 stage pixels and the row was about 43, so its padding is tightened to fit rather than the row being allowed to clip a sprite. That is a measurement, not a taste — tools/probe_pvpui.py asserts the HUD overlaps nothing else drawn, which is what caught the first placement.

The stamp means “locked in”

  • No stamp until the moves are committed. The wax stamp was painted on the decree unconditionally, so the order read as sealed while the player was still choosing it. In PvP the lock is netWait — the moves are committed and the round is waiting on the opponent.
  • The lock-in button looks pressed once it has been, reads MOVES LOCKED, and stops inviting a second press. pvpNetCommit() already returned early while netWait was set, so this only makes the screen agree with what the code was doing.
  • Outside PvP there is no frame to show one. The decree closes the instant lockIn() runs, so the gate is simply false there.

Client: confirmLocked and the confirmBtn* values in play/app.js; the HUD and decree in play/markup.html. Probe: tools/probe_pvpui.py — BEFORE 4/4, AFTER 8/8.

A late reply from a finished match cannot write

Both networked PvP paths — pvpNetCommit() and pvpNetPoll() — read state.pvp once, at entry, and then await the network. pvpNetCommit retries netSet up to three times with 400 ms between attempts and then the round announce up to three times with 500 ms between attempts, so it can be in flight for several seconds. The match can end inside that window — an opponent forfeits, a side is wiped, the Bo3 is decided — and pvpMatchOver() sets pvp:null.

Every continuation that then resumed wrote with Object.assign({}, p.pvp, {…}). Object.assign ignores a null source, so the state was not left null: it was resurrected as {netWait:false, oppC:false} — truthy, with no games, no opp, no net. Six sites did this.

The rule now is identity, not presence:

  • pvpAlive(mid) answers “is the live match still THAT match”, comparing state.pvp.net.mid against the id the call was fired under. Not “is there a pvp object”.
  • pvpPatch(mid, patch) returns a React updater that yields null — a no-op — when it is not. That is what stops a null pvp being resurrected.
  • Both async paths capture const _mid = v.net.mid at entry. All six writes, both desync forfeits, the opponent-forfeit path and both lockIn() callbacks are guarded by it.

Why the match does not instead wait for the server before ending (D's ruling, 2026-08-08). Waiting cannot fix this: however long the deadline, a reply can always land one moment after it. Worse, the most common reason a match ends is an opponent vanishing, so a match that ends only on a reply would freeze the player owed the win — the exact failure the 2026-08-06 “a PvP snapshot is not authority” work removed. The fix is that a late reply cannot write, not that it is unlikely to arrive.

A pvp object that is not a match cannot route a fight

pvpReal(v) is !!(v && v.opp && Array.isArray(v.games)). Four things key off it, because each one changes what a fight is:

  • endRound()'s PvP branch — otherwise a PvE party wipe entered the Bo3 machinery.
  • battleKindNow() — otherwise a PvE fight was persisted to the PvP localStorage slot, and tryResumeBattle(null) tries 'pvp' first, so a reload resumed straight back into it.
  • persistBattle()'s slot choice and the battle log's kind.

A truthy pvp also hides Auto-Battle, which is what players saw first.

Match end and the round watchdog cannot take the fight down

  • pvpGameEnd() and pvpForfeitWin() build with (v.games || []).concat([…]), never v.games.push(…). A match-end path is the only way out of a fight, so it must not be able to throw on a malformed object.
  • endRound()'s catch is a watchdog, and a thrown round is not a live round. If nobody on the player's side can act, it ends the fight and clears the battle snapshot instead of returning the player to 'select' with a dead party — moves visible, none selectable, and the next endRound() throwing in the same place.

Client: pvpAlive, pvpPatch, pvpReal, pvpNetCommit, pvpNetPoll, pvpGameEnd, pvpForfeitWin, persistBattle, battleKindNow and endRound in play/app.js. Probe: tools/probe_r64.py (9/9, including a control that a live match still takes its own reply, and one that a clean PvE defeat is untouched). Replayer: tools/_r64_patch.py.
