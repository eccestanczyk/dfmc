CLIENT SHELL & PLATFORM RENDERING

Other Systems › Client Shell

How the game fits itself onto a screen. The whole UI is authored on one fixed 1920×1080 canvas and scaled to the device; the shell page around it owns loading, fullscreen, scroll pinning, platform quirks, and pushing every connected client onto a new build. These behaviours live in the hand-maintained shell, not in the generated screens.

The stage & text fitting

  • One canvas, one number — the stage is a fixed 1920×1080 box. On boot and on every resize the client computes fitScale = min(viewportWidth/1920, viewportHeight/1080) and applies it to the stage as CSS zoom. Roughly 0.92 on a desktop monitor, ~0.36 on a phone held landscape.
  • Aspect is preserved — one uniform factor for both axes; a mismatched screen letterboxes rather than stretches. Portrait phones letterbox heavily, which is why fullscreen carries an orientation lock (below).
  • Text fitter, horizontal — every element styled with text ellipsis is measured after each render; if its text overflows its box by more than 1px, its font shrinks proportionally, floored at 11.5 stage px (one retry step lower at 11). The original size is cached and restored when the text fits again.
  • Text fitter, vertical — a fixed-height card marked as a fitbox shrinks all of its text together in 6% steps, down to a floor of 72% of authored size (min 11 stage px), instead of clipping.
  • Stage units, not screen units — all fitter floors are in stage px and render at fitScale of that on screen. Sizes chosen for readability must be chosen in stage units with the phone scale in mind.

Platform: iOS text autosizing (the gate)

iOS Safari inflates font sizes on its own (“text autosizing”), and it boosts explicitly-set pixel sizes too. That breaks the text fitter's contract — the size the fitter writes is not the size that renders — so the fitter measures boosted text, shrinks it, Safari boosts the result, and the cycle repeats on every render. The visible symptom is a warped UI: text bursting out of boxes that are themselves correct. Desktop browsers never autosize, and Chrome on Android stands its boost down on pages with a device-width viewport meta (this page has one), so the fault is iOS-only.

  • The fix — text autosizing is switched off (text-size-adjust: 100%) so the fitter's number is the rendered number.
  • Gated to iOS by ruling — D ruled (2026-08-23) that desktop and Android must not change in any way, so the rule only applies when the shell has tagged the page as iOS. No tag, no rule — every other platform renders byte-identically to before.
  • The tag — set in the shell head, synchronously, before first layout: the platform reports as iPhone/iPad/iPod, or reports as Mac while the device has a multi-touch screen. iPadOS 13+ masquerades as a Mac but keeps its touch points; no real Mac has a touchscreen. Touch-screen Windows laptops and all Android devices report neither form and never match.
  • Third-party iOS browsers are covered — Chrome, Firefox and Edge on iOS are WebKit underneath, report Apple platforms, and warp the same way; they get the fix.
  • The future app wrapper inherits it — an iOS app shell is a WKWebView: same engine, same platform strings, same tag, nothing to reconfigure.
  • Fails safe — an exotic browser reporting neither form gets no tag and renders exactly as today.

Scroll pin

  • The document itself must never scroll, not by one pixel — a scrolled document slides the centred stage off-screen and takes corner controls with it while fixed-position elements stay put.
  • Two guards: the stage wrapper is viewport-anchored (fixed) so it cannot drift, and the shell resets any document scroll offset to 0 on every scroll and resize event. overflow:hidden alone does not stop programmatic or focus-driven scrolling.

Fullscreen & orientation

  • A fixed corner button toggles fullscreen. On handheld devices only (coarse pointer, no hover — touch-screen laptops excluded), entering fullscreen also requests a landscape orientation lock, because the 16:9 stage letterboxes a portrait phone to a stamp. Exiting fullscreen releases the lock. Platforms without orientation lock (iPadOS Safari) still get fullscreen.

Build watcher

  • Every connected client polls its own environment's build fingerprint every 45s (release watches release, dev watches dev). On a new build: out of battle the client saves and reloads itself; anywhere a silent reload would cut across live play, the game halts under a full-screen refresh button instead.

Opening a unit’s sheet in battle

Status: the three-tap route is LIVE on release since 2026-09-02 (0.67). Two ways in, one rule for every pointer:

  • Hold a living unit for 450 ms (mouse). The release click is swallowed so the hold never also selects or targets.
  • Three taps on the same living unit, each within 600 ms of the last (mouse or touch). The first two still do what a tap does — select an ally, pick a target — and the third opens the sheet instead. Taps on two different units never add up.

Why two: a phone cannot hold. Touch browsers deliver the compatibility mouse-down and mouse-up together after the finger lifts, so the 450 ms timer is cancelled the instant it starts and a phone had no way into a unit’s sheet mid-fight. The rule is not device-sniffed; a desktop triple-click reaches the sheet too.
