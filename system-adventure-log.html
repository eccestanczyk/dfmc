ADVENTURE LOG

Other Systems › Adventure Log

A permanent, chapter-bound chronicle of everything that has ever happened on the account — hatches, advancements, breedings, floor clears, boss kills, deaths, realm events, and every battle fought. The log itself never forgets; only the depth of battle detail is pruned over time.

Architecture — events, not text

  • The log is an append-only event stream, not stored prose. Each entry is a compact record: {timestamp, event_type, param_ids[]} — e.g. {t, HATCH, DFMC-042}, {t, ADVANCE, DFMC-044 → DFMC-045}, {t, FLOOR_CLEAR, 17}.
  • Display text is rendered at view time from string templates plus codex CSV data. Renaming a creature or rewording a template retroactively fixes the entire history.
  • Cost per event: ~50–100 bytes. A heavy player producing 500 events/day for a full year is ~180k events ≈ 15–20 MB in SQLite — negligible.
  • Storage: one local SQLite database, append-only, indexed on date. No server round-trips to read the log.

Chapters

  • Chapters are dated views, not separate documents. A chapter is simply a date-range query (WHERE ts BETWEEN x AND y) against the single event table.
  • The chapter list UI shows one entry per active day (or per zone milestone on the same screen). Opening a chapter loads only that chapter's events, paginated — the full history is never held in memory.
  • Because chapters are queries, they cost nothing extra to store and can be re-cut later (per-day, per-zone, per-season) without touching the data.

HATCH ALL is one event

  • A single-egg hatch writes HATCH (or MUTANT_HATCH) with the full per-creature fields. The soul bag's HATCH ALL button does not: however many eggs it opens, it writes exactly one HATCH_BATCH.
  • The batch carries the hatchling count, the grade tally of what came out, and the species breakdown sorted by count, capped at six entries with +n more beyond that. The cap is a storage rule, not a display one — the string is written at hatch time and lives in the save forever.
  • A mutant is exempt. Any mutant in the batch still writes its own MUTANT_HATCH line alongside the batch line, and is also counted in the batch's mutant tally. Mutants are story events and are rare enough to deserve the room.
  • Rationale: one press of HATCH ALL on a full soul bag wrote 85 separate events, which buried the chapter it landed in and was then carried in every save from that moment on.

Param IDs reference codex CSVs; the log stores no names or descriptions. Ordinary per-battle XP ticks are not logged as separate events — they live inside the battle summary.

Battle Logs (sub-item of the Adventure Log)

  • Battles are not deterministic, so full turn-by-turn data must be recorded — there is no seed-replay shortcut.
  • The adventure log itself holds only a battle summary row: participants, result, turn count, rewards, and a battle_id.
  • Full detail lives in a separate table keyed by battle_id: an array of compact turn-action structs {actor_id, move_id, target_id, damage, flags} at ~20–40 bytes each. A 30-turn battle ≈ 1–3 KB raw.
  • Each battle's turn array is serialized and gzip-compressed as one blob (3–5× reduction) before storage. Nothing is decompressed until requested.
Renderers degrade, never break. Every field above is optional at render time: a log written before a field existed still reads correctly, it just says less — "A creature hatched: Cairn." is a valid line from an old save. Adding a field to an event therefore never needs a migration, and old chapters are never rewritten.

Viewing a battle log

1 — Tap

The player taps the Battle Log button on a battle summary row in a chapter.

2 — Fetch & decompress

The blob is fetched by battle_id and decompressed in memory (<1 ms for a 1–3 KB blob) — only that one battle, never the rest of the history.

3 — Render

Turn structs are deserialized and rendered into readable turn-by-turn text via templates + codex data. Compression is invisible at the UI layer.

  • Compaction deletes only the detail blob; the summary row (and therefore the chapter narrative) is never lost — the log loses replay depth, not history.
  • After compaction, the Battle Log button on an old wild battle shows the summary card with a "detail expired" state instead of turn-by-turn text.

Storage budget — compress, never discard

Nothing is ever deleted. Every event and every battle's numbers are kept for the life of the account, because they are balancing data to be pulled off real players. What changes with age is how they are stored.

AgeFormCost
Newest 500 eventsExpanded in advChapters, rendered in the log window~68 bytes each
Older eventsPacked one-per-line and gzipped into advArc blocks (base64). Falls back to the plain packed string where CompressionStream is unavailable — still complete, just larger~7 bytes each, a ~10× cut
Newest 25 battlesFull round-by-round log, last 10 rounds~5 KB each
Battles 26–200Compact row: result, floor, XP, Food, participants. The prose goes, the numbers stay~290 bytes each
Older battlesArchived into advArc as BATTLEROW entries. The chapter line falls back to the BATTLE event's own stub~7 bytes each

Measured on the two worst real accounts, with the full history intact in both cases: 905 KB → 373 KB (500 live events + 3,380 archived in 38 KB) and 638 KB → 317 KB. Applied on write and on load, so an oversized save shrinks the moment it is opened.

High-frequency events use one-letter keys — {c:37,g:{Worn:22},y:'+148 Scrap'} — and a bulk action is always one event: dismantling 113 eggs costs one line with a grade tally, never 113 lines.

Reading the archive

The archive is DEVICE-LOCAL and does not reach the server. The Stage 4a save diet strips advArc, advChapters, advBattles and floors from every upload — they were 89% of a real save's bytes, and advArc riding the upload was itself the 2026-08-01 save-ceiling incident (68,560 B of a 127,115 B save; /api/save refuses over 131,072 B). So /api/backup/export does not carry log history, and a new device starts with an empty log. Pulling history off a player is the on-demand advlog extraction round (admin-backend.html §8). Each block is {n, z} (gzip, base64) or {n, t} (plain), plus the day index below. Unpack a block's text into events by splitting lines on \n and fields on \x01 — ts, TYPE, JSON params:

import gzip, base64, json
for b in save.get('advArc', []):
    txt = gzip.decompress(base64.b64decode(b['z'])).decode() if 'z' in b else b['t']
    for line in txt.split('\n'):
        ts, typ, params = line.split('\x01'); ev = (ts, typ, json.loads(params))

The day index — how a per-day view is possible at all

On DEV, not yet on release. A packed event carries only ts = HH:MM. The DATE lived on the chapter object, and advTrim drops a chapter the moment its last event is archived — so the archive was a single undated stream. Nothing was ever lost; the history simply could not be cut into days. That is the whole of “the log only shows a day”.

  • DAY marker. advTrim writes {ts:'00:00', type:'DAY', params:{k:<dayKey>, t:<date>, c:<chapter title>}} into the packed stream when the day changes and whenever a fresh block opens. Every event after a marker belongs to that day until the next marker.
  • Every block is self-describing. The marker at each block head is the load-bearing half: without it a block that opens mid-day loses its leading non-battle events. Measured at 14 of 156 on a real-shaped day before the rule was added.
  • Block header, never compressed. d is the list of dayKeys the block holds; dl is the last day it declared, so the next append knows whether it owes a marker. A day grid is drawn from d across all blocks with zero decompression; opening one day decompresses only the blocks whose d lists it (measured: 2 of 5 worst case, 0.7 average over 30 days).
  • Marker is the truth, d is a cache. A reader that finds them disagreeing trusts the marker and repairs the header.
  • advArcCompact re-declares the running day at the head of every regrouped block. The heal splits blindly by index, so without this it destroys the index it exists to carry.
  • A BATTLEROW is a RECORD, not a log entry. It is the compacted detail its BATTLE line points at, is looked up by id, and must never be rendered or counted as an event — doing so double-counts every archived day.
  • NEVER date an event from its battle id. A battle_id is 'B-' + Date.now().toString(36) — epoch ms, i.e. UTC — while a chapter's dayKey is toDateString(), the device's LOCAL date. At UTC+9 a 07:00 battle decodes to the previous day, so id-dating puts every morning on the wrong tile. Id-dating survives only as an approximate rescue for archives written before markers existed, where it is accurate to within one day at the boundary.
  • Cost. One marker per day plus one per block: 1.9% of the archive. A marker per moved slice would be a marker per event — once the live window is full advTrim runs on every event and moves exactly one — which measured 7.4%, the same shape as the 2026-08-01 gzip-per-single-event mistake.
  • Ceiling. Web Storage is ~5 MiB per origin and the local slot is written twice (a once-per-session _bak copy), so the practical budget is ~2.5 MB against a ~102 KB non-log save. At ~37 B per archived event that is roughly 57,000 events. A full store raises QuotaExceededError, which the local save path currently swallows into a console warning.

Legacy archives have no markers and no headers, and those dates no longer exist — they are not reconstructed, only grouped as one “Earlier” range.

  • 2026-08-01 — the archive packs before it compresses, and rows keep their time. Overflow was gzipped and base64'd the instant it happened, and once the live window is full the overflow is exactly one event — so a 405-event archive was 405 single-line blocks. gzip has nothing to find in a 100-byte line and costs an ~18-byte header, then base64 adds a third on top: measured 40,912 B of text stored as 68,560 B, larger than not compressing at all, where one packed block is 7,856 B. Events now land in a trailing plain block and are sealed into gzip only at 16 KB, and a fragmented archive is re-packed once on load (405 blocks → 2, every event preserved). Archived battle rows were also being built with an empty ts field and losing their time — 275 of 405 in a live save; the row now carries the timestamp stamped when the battle was recorded.

HATCH and MUTANT_HATCH now carry grade, sex, the egg's grade and where the egg came from (bred in pen N, or found on floor N); ADVANCE carries the level and stage it happened at; LEVEL_UP carries the level it came from; BOSS_DEFEATED carries floor, rounds and how many of the party were still standing; DEATH carries floor, killer and rounds.
