MOBILE SHELL

Workflow › Mobile Shell

The phone build (board N4): the same web client, inside a Capacitor 8 shell for Android and iOS, the way the Steam / desktop shell wraps it for the download. One project, both stores. Spec, store rules and the lane plan live in the client repo, docs/mobile-app-2026-11.md; this page is the shell's working notes. Nothing here is live for players yet.

The shape

  • Bundled, not a website in a frame — the app ships play/ (the page, the stage code, the UI art, fonts, music) and the codex tables inside the binary, at the same dfmc pin the web release reads. Apple’s 4.2 (“minimum functionality”) is what this buys: the game opens from the binary, and a bad connection meets the shell’s own screen, never a WebKit error page.
  • The page’s origin is the shell’s — https://localhost on Android, capacitor://localhost on iOS. Only /api/* leaves, to https://playdfmc.com, with the bearer session of the auth handoff (Networking).
  • Creature art streams — the bundle carries the UI art and leaves the heavy families out: creature cut-outs, tiles, mutant recolours, ground plates and the boss paintings (132 MB at the 2026-11-05 pin) are read from the R2 art bucket at the pin, immutable, and the WebView’s HTTP cache keeps what it saw. The Android bundle is 51.6 MB; the Play / App Store cellular prompt is at 200 MB.
  • Landscape only, no status bar — locked in the native projects (sensorLandscape, landscape-only Info.plist) and again by the bridge at boot. The rotation veil of the web build never shows.
  • Keyboard never shrinks the game — the WebView keeps its size while the keyboard is up (Capacitor Keyboard resize: none); the T36 D3 strip can’t happen.
  • Sign-in in the system browser — a sign-in door opens a Custom Tab / Safari sheet (Google refuses a WebView), the provider sends the browser home to herumon://auth?code=…, the OS hands that deep link to the app, and the page swaps the one-time code for its bearer session. The worker allow-lists herumon:// as a handoff target.
  • Store bridge is a placeholder — DFMC_SHELL.store names the provider (Apple / Google) and no buy, so the client hides the pack grid until the StoreKit 2 / Play Billing lanes exist and D’s store accounts do.

The bridge (window.DFMC_SHELL)

Same names as the Steam shell’s, read by the same lines of the client. mobile/src/shell.js in the client repo holds the shapes: kind 'mobile', platform (android / ios), dataBase (the bundled tree), artBase (the R2 pin root), streamed (the paths that read from it; everything else is local), apiBase, handoff 'herumon://', authCode(fn), store, steam false, version, bundle, channel 'mobile', restart(), onResume(fn). The shell itself hides the status bar, locks landscape, holds the splash until first paint, opens external links in the system browser and draws the NO CONNECTION plate.

Build and toolchain

  • Copier — tools/mobile_bundle.py --platform android|ios builds mobile/www/ from the dfmc repo at the pin (git objects only, the working tree untouched) and play/; Android leaves the AAC audio copies out (its WebView plays Ogg), iOS keeps both. Then npx cap sync.
  • Android — Gradle project under mobile/android/, needs a JDK 21 and the Android SDK (API 36). The dev PC had neither on 2026-11-05; the spec’s § 7.1 lists the installs. iOS builds only on a Mac with Xcode 26 (SPM, no CocoaPods).
  • Gate — tools/probe_capshell.py: the project settings, the copier’s output (size, zero CDN URLs in the bundled page, every streamed family absent), no secret in the committed files, the bridge shape against a stub Capacitor (status bar, orientation, deep link, offline plate, system browser), and the real client booted from the bundle with every table and UI image local, every creature / plate image at the pin on R2, zero jsDelivr. The emulator build and the sign-in round trip are the device step that follows.

Open

  • Emulator build + sign-in round trip (needs the SDK on the dev PC).
  • Phone-fit (lane 4): keyboard behaviour on device, maximum-scale, the stage fit in a fixed WebView, safe areas on a notched iPhone.
  • Sign in with Apple (lane 5), StoreKit 2 / Play Billing (lanes 6-7), push (8), the store listings (9) — all wait on D’s Apple / Google accounts.
  • The Android page origin https://localhost matches the client’s dev-environment test (DEVENV); the data path is unaffected under a bundled tree, but anything else that reads that flag should be checked on device.
